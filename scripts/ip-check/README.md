# 카드 IP 점검

노션 카드 DB 의 「IP 점검」 을 매일 채운다. 기준은 [`docs/store-release.md`](../../docs/store-release.md) 6-1.
돌리는 곳은 claude.ai 클라우드 루틴 「카드 IP 점검 (이름 · 그림)」 (매일 09:00 한국 시간, 노션 커넥터). 루틴에 넣는 지침은 [`routine-prompt.md`](routine-prompt.md).

## 누가 무엇을 정하나

정답이 있는 부분은 스크립트가 정하고, AI 는 그 결과를 그대로 쓴다. 정답이 없는 부분만 AI 가 판단하고, 그 결과도 쓰기 전에 스크립트가 검사한다.

| 일 | 누가 | 어떻게 확인하나 |
| --- | --- | --- |
| 대상 카드 고르기 | AI — SQL 한 번 | SQL 이 지침에 고정 |
| 이름 상표 (6-1 1번) | `ip_check.py names` | 시작 기준치(카나리아) — 정답을 아는 이름이 정답대로 나와야 진행 |
| 욕설 · 저속한 유머 (5번), 그림 (2 ~ 4번) | AI | 애매하면 미점검. 「수정 필요」 는 카드 댓글로 사람이 본다 |
| 「IP 점검」 에 쓸 값 | AI 가 계획을 만들고 `ip_check.py validate` 가 검사 | 아래 「쓰기 전 검증」 |
| 쓴 뒤 | `ip_check.py verify` | 노션을 다시 읽어 계획과 비교 |

## 흐름

```
SQL → cards.json
names    → names.json      카나리아 실패 · KIPRIS 접속 불가 → 종료 2 → 아무것도 안 씀
AI 판단  → plan.json       (5번 · 그림)
validate                   하나라도 어긋나면 종료 1 → 아무것도 안 씀
노션에 plan 대로 쓰기 · 댓글
SQL 다시 → actual.json
verify                     어긋나면 끝 보고에 적는다
```

## 기준치 (카나리아)

| 이름 | 정답 | 이유 (2026-11-18 KIPRIS) |
| --- | --- | --- |
| 메이플스토리 | 수정 필요 | 09 · 41류 등록 상표 5건 |
| 무야호 | 통과 | 등록 상표가 있지만 16 · 30 · 32 · 35류 |

API 가 바뀌거나 인코딩이 깨지거나 판정 규칙이 고장 나면 둘 중 하나가 어긋난다 — 그때는 「통과」 를 잘못 퍼뜨리는 대신 멈춘다. 이 두 상표의 상태가 실제로 바뀌면(소멸 등) `ip_check.py` 의 `CANARY` 를 다른 이름으로 바꾼다.

## 판정 규칙

* **상표 (1번)** — KIPRIS 「상표 출원 속보」 `getWordSearch`, 전 기간. 상표명이 카드 이름과 같고(공백 · 문장부호 · 영문 대소문자 무시) 상태가 「등록」 이고 상품분류에 09 또는 41 이 있으면 수정 필요. 결과를 모든 쪽 다 본다.
* **이름 결과** = 1번 · 5번 중 하나라도 수정 필요 → 수정 필요 / 둘 다 통과 → 통과 / 그 밖 → 미점검.
* **합치기** (`merge`)

  | 이름 | 그림 | IP 점검 |
  | --- | --- | --- |
  | 수정 필요 | 아무거나 | 수정 필요 |
  | 아무거나 | 수정 필요 | 수정 필요 |
  | 통과 | 통과 | 통과 |
  | 통과 | 없음 | 그림 대기 |
  | 그 밖 | | 미점검 |

## 쓰기 전 검증 (`validate`)

* 값은 정해진 것만 — 이름 `수정 필요 · 통과 · 미점검`, 그림 `수정 필요 · 통과 · 없음 · 미점검`, IP 점검 `수정 필요 · 통과 · 그림 대기 · 미점검`.
* `after` 가 합치기 표와 같다. 지금 값과 같으면 계획에 넣지 않는다 (쓰면 「마지막 수정」 이 바뀌어 다음 날 또 대상이 된다).
* 상표가 수정 필요면 이름도 수정 필요. 상표가 미점검이면 이름은 통과가 될 수 없다. 호출 상한으로 넘긴 카드는 계획에 없어야 한다.
* 대상 목록에 있는 카드만, 한 번씩만.
* 한 번에 20장 넘게 바꾸지 않는다 (`--max-changes`). 통과 · 그림 대기 → 미점검 이 5장을 넘으면 무언가 고장 난 것으로 본다 (`--max-downgrades`).
* 계획에 KIPRIS 키 값이 없다.

## 파일 모양

```jsonc
// cards.json — SQL 결과 그대로
[{"url": "...", "Name": "죽은 척", "카드 문구": "...", "IP 점검": "미점검", "마지막 수정": "..."}]
// plan.json — 바꿀 카드만
[{"url": "...", "name": "통과", "art": "없음", "after": "그림 대기", "why": "한 줄 이유"}]
// actual.json — 쓴 뒤 다시 읽은 SQL 결과 (url · IP 점검 만 있으면 된다)
```

`names` 출력: `{"ok", "canary", "calls", "errors", "results": {"<이름>": {"result": "수정 필요 | 통과 | 미점검 | 넘김", "hits": [...], "total", "why"}}}`.

## 한계

* KIPRIS 무료 플랜은 월 1,000건 · 2026-12-31 까지 (PM 계정, 1월에 연장). 한 번 실행에 30회 (`--max-calls`, 카나리아 2회 별도).
* 띄어 쓴 이름은 낱말별로 검색돼 결과가 크다 (「죽은 척」 3,709건 = 8회). 5,000건이 넘는 이름은 미점검으로 두고 사람이 KIPRIS 에서 본다.
* 상한으로 넘긴 카드가 「통과」 상태이고 26시간 안에 고친 카드가 아니면 다음 날 대상에서 빠진다 — 끝 보고의 「넘긴 카드」 를 보고 손으로 한 번 더 돌린다.
* 비슷한 이름(한 글자 다름 · 영문 표기)은 보지 않는다. 6-1 1번이 「같으면」 이기 때문.

## 손으로 돌리기

```
KIPRIS_KEY=... python scripts/ip-check/ip_check.py names --cards cards.json > names.json
python scripts/ip-check/ip_check.py validate --cards cards.json --names names.json --plan plan.json
python scripts/ip-check/ip_check.py verify --plan plan.json --actual actual.json
```

키는 KIPRIS Plus 마이페이지 → API KEY 관리. 루틴에서는 클라우드 환경 「Default」 의 환경 변수 `KIPRIS_KEY`. 환경 네트워크 허용 도메인: `plus.kipris.or.kr` · `prod-files-secure.s3.us-west-2.amazonaws.com` (노션 그림 파일). 프록시가 HTTPS 만 통과시킨다.
