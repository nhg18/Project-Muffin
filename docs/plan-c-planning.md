## 0. 결론 먼저 — 기획자의 일은 세 가지다

| # | 일 | 왜 필요한가 | 결과물 |
| --- | --- | --- | --- |
| 1 | **정해지지 않은 것을 정한다** | 기획서에 `미정` 인 항목은 개발자가 구현하지 못한다. 지금 미정 11건이 개발 일정을 막고 있다 | 결정 요청서 → `docs/systems/` 문서의 `확정` |
| 2 | **카드 59장을 완성한다** | 카드 효과의 숫자(N, M) · 이름 · 매수가 전부 비어 있다. 이게 없으면 카드를 만들 수 없다 | 카드 시트 (스프레드시트) |
| 3 | **게임이 맞게 되는지 확인한다** | 규칙을 가장 잘 아는 사람이 확인해야 버그를 찾는다 | 플레이테스트 기록 · 게이트 체크리스트 · 버그 목록 |

기획자가 **하지 않는 것**:

* 코드 구조 정하기 ("이 클래스에서 이렇게 해 주세요") — 기획서는 "무엇이 일어나는가"만 쓴다 (`GDD_GUIDE.md` 8절)
* 색 · 모양 정하기 — UI 디자인 몫. 기획자는 "무엇이 어떤 순서로 보여야 하는가"를 정한다
* 노션 · 디스코드에서 합의하고 끝내기 — **`docs/systems/` 에 `확정` 으로 옮겨야 개발이 시작한다**

## 3. 결정 요청서 — 모든 결정은 이 양식 하나로

노션 「결정 로그」 데이터베이스에 한 결정당 한 페이지. 아래 양식을 복사해 쓴다.

```
제목: [결정 #번호] 무엇을 정하는가 (한 줄)
담당: 기획 R / 기획 X
상태: 초안 → 검토 중 → 확정 / 보류
마감: YYYY-MM-DD
관련 문서: systems/xx-xxx.md 몇 절

1. 질문
   정해야 하는 것을 한 문장으로.

2. 왜 지금 정해야 하나
   이게 없으면 누가 무엇을 못 하는가. (development-plan.md 4-1절 "막는 것")

3. 선택지 (2~3개)
   가) ...  — 좋은 점 / 나쁜 점
   나) ...  — 좋은 점 / 나쁜 점
   다) ...  — 좋은 점 / 나쁜 점

4. 개발 코멘트 (개발자가 회의 전날까지 채움)
   가) 난이도 상/중/하 — 이유 한 줄
   나) ...

5. 추천안과 이유
   플레이테스트 결과가 있으면 같이 적는다.

6. 결정 (회의에서 채움)
   무엇으로 정했나 / 결정일 / 결정한 사람

7. 반영
   systems/ 문서 PR 링크
```

### 예시 — 결정 #1 덱 구성 (틀을 보여주는 예시일 뿐, 실제 결정이 아니다)

```
제목: [결정 #1] 덱에 카드를 몇 장씩 넣는가
담당: 기획 R   마감: 10/4   관련: systems/05-deck.md 2절 · 11절

1. 질문: 카드 59종을 각각 몇 장씩 덱에 넣는가? 총 몇 장인가?
2. 왜 지금: 로직 개발이 게임 시작 시 덱을 만드는 코드(A1-6)를 10/11 까지 만든다.
   매수가 없으면 테스트용 가짜 덱으로만 만들 수 있다.
3. 선택지
   가) 59종 × 1장 = 59장 — 단순. 4인이면 시작에 20장이 나가 덱이 39장만 남는다
   나) 행동 2장 · 카운터 2장 · 함정 1장 = 101장 — 반응 카드가 자주 나온다. 덱이 두껍다
   다) 카드마다 1~3장 차등 (기본 공격 · 회복은 3장, 강한 카드는 1장) — 밸런스를 잡기 쉽다. 정할 게 많다
4. 개발 코멘트: (로직이 채움)
5. 추천: 다) — 종이 테스트에서 가) 는 반응 카드가 너무 드물었다 (금요일 테스트 기록 참고)
```

**좋은 결정 요청서의 조건**: 선택지가 2개 이상이다. "막는 것"이 적혀 있다. 숫자가 있다. 추천에 이유가 있다.

## 4. 종이 프로토타입 만드는 법

카드 게임은 **코드 없이 종이로 먼저 시험할 수 있다.** 개발을 기다리지 않고 수치와 규칙을 확인하는 가장 빠른 방법이다.

1. 명함 크기 종이(또는 포스트잇)에 카드를 적는다. 한 장에: **ID · 종류(행동/카운터/함정) · 대상 · 효과 · 숫자**
2. 처음에는 MVP 6장만 쓴다 — A09(데미지) · A08(회복) · A06(드로우) · A05(버리기) · C05(무효화) · T06(피해 반응 함정). 매수는 결정 요청서의 선택지대로
3. HP 는 메모지에 숫자로 적고, 체인은 카드를 겹쳐 쌓는다. 반응 5초는 스마트폰 타이머
4. 규칙은 `systems/` 문서 그대로 따른다. 문서에 없는 상황이 나오면 **그 자리에서 정하지 말고 기록한다** — 그게 결정 요청서 후보다
5. 한 판이 끝나면 5절 양식으로 기록한다

카드가 늘면(M2 이후) 11-card-list 의 카드를 계열별로 조금씩 추가한다.

## 5. 플레이테스트 진행 · 기록

**매주 금요일 40분.** M1 ~ M2 는 종이, M2 게이트 이후는 빌드(개발자가 띄워 준다).

진행 순서: 이번 주 확인할 것 발표(3분) → 플레이(25분) → 느낀 점 한 사람씩(10분) → 결정 요청서 후보 정리(2분)

기록 양식 (노션 「플레이테스트」 데이터베이스):

| 항목 | 내용 |
| --- | --- |
| 날짜 · 참가자 · 종이/빌드 | |
| 이번에 확인하려던 것 | 예: A09 데미지 20 이 너무 센가 |
| 결과 | 판 수, 걸린 시간, 누가 어떻게 이겼나 |
| 숫자 | 한 판 평균 턴 수, 찹츄 선언 횟수, 사망까지 걸린 턴 |
| 이상했던 점 | 문서에 없는 상황, 재미없던 순간, 너무 강한 카드 |
| 버그 (빌드일 때) | 무엇을 했더니 → 무엇이 됐고 → 무엇이 돼야 했나 |
| 다음 행동 | 결정 요청서 후보, 수치 조정 후보 |

## 6. 카드 시트 · 밸런스 시트 (기획 R)

**카드 시트**는 59장의 원본이다. UI 개발이 이 시트에서 Unity 카드 에셋을 만든다 (M4). 공유 스프레드시트 한 장, 한 줄에 카드 한 장.

| 열 | 예 | 비고 |
| --- | --- | --- |
| ID | A09 | 11-card-list 그대로 |
| 이름 | (예) 물어뜯기 | 카드 디자인이 카드에 넣는다. 최대 8글자 (`plan-d-art.md` 2-1) |
| 종류 | 행동 / 카운터 / 함정 | |
| 대상 | 상대 1명 | 04-card 11절의 대상 타입 |
| 조건 | 본인 턴 + 메인 행동 미사용 | |
| 효과 문구 | 대상의 HP 를 20 줄인다. | **카드에 그대로 찍히는 문장.** 3줄 · 45글자 안팎 |
| N | 20 | |
| M | — | |
| 매수 | 3 | 결정 #1 |
| 상태 | 확정 / 제안 / 미정 | GDD_GUIDE 7절 표기 |
| 일러스트 | 고유 / 공용(계열) | 카드 디자인과 협의 |
| 메모 | 종이 테스트에서 너무 셌음 → 25 에서 20 으로 | |

**밸런스 시트**는 플레이테스트 숫자를 모은다: 카드별 사용 횟수 · 승리한 사람이 쓴 카드 · 평균 게임 길이. M6 에 외부 테스트 결과로 수치를 조정할 때 근거가 된다.

> 11/4 까지 카드 시트 59장 전부 `확정` 이 목표다. 매주 10장 정도씩 확정하면 된다.

## 7. 카드 테스트 케이스 표 (기획 R, M4)

로직 개발이 카드 효과를 자동 테스트로 만들 때 쓰는 표다. 카드마다 2~3줄, **"이 상황이면 → 이렇게 돼야 한다"** 만 쓴다.

| 카드 | 상황 | 기대 결과 |
| --- | --- | --- |
| A09 | P1(HP 100)이 P2(HP 100)에게 사용, 아무도 반응 안 함 | P2 HP 80. A09 는 버림 더미로 |
| A09 | P2 HP 10 에게 사용 | P2 HP 0, 사망 대기 상태 |
| A09 + C05 | P1 이 P2 에게 A09, P2 가 C05 로 반응 | P2 HP 100 그대로. A09 · C05 모두 버림 더미로 |

위 숫자(20 등)는 설명용 가정이다. 실제로는 카드 시트 값을 쓴다. 이 표가 있으면 개발자가 규칙을 해석하는 시간이 크게 준다.

## 8. 게이트 체크리스트 (기획 X)

마일스톤 끝마다 "되는지 확인"을 기획 X 가 진행한다. 개발자가 빌드(4클론 또는 실기)를 띄우고, 기획 X 가 항목을 하나씩 확인해 표시한다.

양식: 노션 체크리스트 — `번호 · 해야 할 행동 · 기대 결과 · 통과/실패 · 실패 시 무엇이 보였나`

### 예시 — M1 게이트

| # | 행동 | 기대 결과 |
| --- | --- | --- |
| 1 | 4명이 같은 방에 들어가 방장이 시작 | 4명 모두 게임 화면으로 넘어간다 |
| 2 | 시작 직후 각자 손패 확인 | 전원 5장. 네 사람의 카드 구성이 서로 다르다 (섞였다) |
| 3 | 좌석 확인 | 모든 좌석에 HP 100 · 손패 5 가 보인다. 네 화면이 같다 |
| 4 | 첫 턴 확인 | 한 사람에게만 초록 테두리. 네 화면에서 같은 사람이다 |
| 5 | 다시 한 판 | 첫 턴이 지난 판과 다른 사람일 수 있다 (무작위) |

실패 항목은 버그 목록에 올린다: **무엇을 했더니 → 무엇이 됐고 → 무엇이 돼야 했나**, 스크린샷 1장.

## 9. `docs/systems/` 문서 고치는 법 (GitHub 웹)

프로그램 설치 없이 브라우저에서 한다. 처음 2번은 UI 개발이 옆에서 같이 한다.

1. GitHub 저장소 → 브랜치를 `develop` 으로 → `docs/systems/` → 고칠 파일 클릭
2. 오른쪽 위 연필(✏️) 아이콘
3. 고친다. 표는 `|` 로 칸을 나눈다. 모든 규칙과 숫자 옆에 `확정` / `제안` / `미정` 을 붙인다 (`GDD_GUIDE.md` 7절)
4. 문서 맨 위 **최종 수정일**을 오늘 날짜로 바꾼다
5. 아래 "Commit changes" → **"Create a new branch … and start a pull request"** 선택 → 제목에 `docs(systems): 결정 #번호 무엇 확정`
6. PR 화면에서 Reviewers 에 해당 개발자 1명 지정 (규칙 → 로직 개발, 화면 → UI 개발)
7. 리뷰가 끝나면 개발자가 머지한다

> 새 문서를 만들 때는 비슷한 기존 문서를 복사해서 틀을 따른다. 결과 화면 문서는 `07-win-condition.md` 9절과 `16-room-ui.md` 를 참고한다.

| PR | "이렇게 고쳤으니 봐 주세요" 요청. 리뷰가 끝나야 반영된다 |
| SO (ScriptableObject) | Unity 의 데이터 파일. 카드 1장 = SO 1개. 숫자를 바꾸기 쉽다 |

## 12. 막힐 때

* **문서에 답이 없다** → 결정 요청서 후보로 적고 월요일 회의에 올린다. 혼자 정해서 개발자에게 말로 전달하지 않는다
* **개발자에게 물어볼 게 있다** → 기획 R 은 로직 질의응답 시간, 기획 X 는 UI 개발에게 디스코드. 질문은 "무엇이 궁금한가 + 내가 생각한 답" 형식으로
* **마감을 못 맞출 것 같다** → 월요일 회의에서 바로 말한다. 늦게 말할수록 개발이 더 오래 멈춘다
* **AI(Claude)를 써도 된다** → 결정 요청서의 선택지 정리, 문서 문장 다듬기에 쓴다. 단, AI 가 정한 값은 `제안` 이다 (`GDD_GUIDE.md` 7절)
