# 기획 문서 작성 지침 (GDD Guide)

> 대상: 기획 문서를 작성·수정하는 모든 사람과 AI.
> 결과물 위치: `docs/systems/*.md`
> 개발 지침은 [`../CLAUDE.md`](../CLAUDE.md).

---

## 1. 역할

당신은 게임 개발 프로젝트의 **게임 기획자이자 개발 문서 작성 보조 AI**입니다.

목표는 보기 좋은 기획서를 만드는 것이 아니라, **개발자가 문서를 보고 바로 구현할 수 있는 수준의 명확한 기획 문서**를 만드는 것입니다.

기획 내용은 항상 실제 게임 개발 가능성을 고려하여 작성합니다.

---

## 2. 가장 중요한 원칙 — 개발자가 바로 이해할 수 있게

기획을 추상적인 표현으로 작성하지 않습니다.

| 나쁜 예 | 좋은 예 |
| --- | --- |
| 플레이어가 재미있게 이동한다 | 플레이어는 WASD 입력으로 8방향 이동한다. 이동 속도는 5m/s이다 |
| 적이 적절한 난이도로 공격한다 | 적은 플레이어와의 거리가 8m 이하가 되면 추적을 시작한다 |
| 전투가 긴장감 있게 진행된다 | 적의 공격 사거리는 2m, 공격 쿨다운은 1.5초이다 |

**"무엇을 한다"뿐 아니라 "언제, 누구에게, 어떤 조건에서, 어떤 결과가 발생하는지"를 명확하게 작성합니다.**

---

## 3. 문서가 답해야 하는 질문

* 무엇을 만드는가?
* 플레이어가 무엇을 하는가?
* 게임 규칙은 무엇인가?
* 각 시스템은 어떻게 동작하는가?
* 어떤 조건에서 상태가 변경되는가?
* 플레이어에게 무엇이 표시되는가?
* 어떤 입력을 사용하는가?
* 어떤 예외 상황이 발생하는가?
* 개발자는 무엇을 구현해야 하는가?

문서를 읽은 개발자가 추가 질문 없이 기본적인 구현을 시작할 수 있어야 합니다.

---

## 4. 기능 작성 순서

1. **기능 목적** — 이 기능이 왜 존재하는지
2. **동작** — 플레이어 행동과 시스템 반응을 순서대로
3. **조건** — 실행 조건
4. **결과** — 어떤 값/상태가 변경되는지
5. **예외** — 일반적이지 않은 경우
6. **UI** — 화면에 무엇이 표시되는지
7. **수치** — 가능하면 구체적인 숫자

---

## 5. 시스템 단위로 분리

게임 전체를 하나의 긴 문서로 설명하지 않습니다. 시스템 단위로 파일을 나눕니다.
각 시스템 문서는 **독립적으로 읽어도 이해할 수 있어야** 합니다.

현재 분할: `docs/systems/README.md` 참고.

---

## 6. 상태와 흐름 우선

상태가 존재한다면 가능한 상태와 전환 조건을 명확히 씁니다.

```
Lobby → Room → Ready → GameStart → Playing → GameEnd
```

조건이 여러 개면 표를 사용합니다.

| 현재 상태 | 조건 | 다음 상태 | 결과 |
| --- | --- | --- | --- |
| Idle | 공격 입력 | Attack | 공격 실행 |
| Attack | 공격 완료 | Cooldown | 공격 불가 |
| Cooldown | 1.5초 경과 | Idle | 다시 공격 가능 |

---

## 7. 수치 표기 규칙 (중요)

모든 수치와 규칙에는 **반드시 구분 표기**를 붙입니다.

| 표기 | 의미 | 구현 가능 여부 |
| --- | --- | --- |
| **확정** | 팀이 결정한 내용 | 구현한다 |
| **제안** | AI 또는 개인이 제시한 값. 승인 필요 | 구현 전 확인 |
| **가정** | 문서를 이어 쓰기 위한 임시 값 | 구현 전 확인 |
| **미정** | 아직 결정되지 않음 | **구현하지 않는다** |

* AI가 임의로 값을 정한 경우 반드시 `제안`으로 표시합니다.
* 서로 다른 구분의 정보를 한 문장에 섞지 않습니다.
* 각 시스템 문서 하단에 `미정 / 결정 필요` 목록을 둡니다.

---

## 8. 기획과 구현을 구분

기획서에서 코드 구조를 강제로 결정하지 않습니다.

| 나쁜 예 | 좋은 예 |
| --- | --- |
| `PlayerController.Move()`에서 `Rigidbody2D.velocity`를 수정한다 | 플레이어는 입력 방향으로 이동한다. 이동 속도는 5이며 대각선 이동 시 속도가 증가하지 않는다 |

단, **구현에 크게 영향을 주는 요구사항은 명시**합니다.

* 모든 플레이어에게 동일하게 보여야 함
* 마스터(서버)가 판정해야 함
* 저장되어야 함
* 프레임마다 갱신되어야 함
* 입력한 플레이어에게만 적용됨
* 해당 플레이어에게만 보여야 함(비공개 정보)

---

## 9. Unity를 고려한 기획

다음 요소가 필요한지 판단해 문서에 표시합니다.

Scene / GameObject / Prefab / ScriptableObject / UI / Input / Animation / VFX / Audio /
Collider / Physics / Network Object / Network State / RPC·Event / Save Data

다만 기획 단계에서 클래스 구조나 디자인 패턴을 결정하지 않습니다.

---

## 10. UI 기획

이름만 쓰지 않고 표로 정리합니다.

| UI | 표시 조건 | 표시 내용 | 동작 |
| --- | --- | --- | --- |
| HP Bar | 항상 | 현재 HP / 최대 HP | HP 변화 시 갱신 |
| 찹츄 버튼 | 손패 10장일 때 | "찹츄!" | 누르면 찹츄 선언 |

표시 위치 / 표시 정보 / 표시 조건 / 숨김 조건 / 입력 / 버튼 동작 / 값 변경 방식을 명시합니다.

---

## 11. 입력 기획

**입력 → 게임 동작**의 관계가 명확해야 합니다.

| 입력 | 동작 | 조건 |
| --- | --- | --- |
| 카드 탭 | 손패 펼치기 | 항상 |
| 카드 드래그 → 드롭 영역 | 카드 사용 요청 | 사용 조건 충족 |

---

## 12. 게임플레이 흐름

각 단계마다 **진입 조건 / 가능한 행동 / 종료 조건 / 다음 단계**를 명시합니다.

---

## 13. MVP 분류

모든 기능을 다음 중 하나로 분류합니다.

| 분류 | 의미 |
| --- | --- |
| **Core** | 게임이 성립하기 위해 반드시 필요 |
| **MVP** | 첫 번째 플레이 가능한 버전에 필요 |
| **Optional** | 없어도 게임이 성립 |
| **Future** | 현재 개발 범위 제외 |

개발 범위가 커지면 기능 추가가 아니라 **MVP 축소**를 먼저 제안합니다.

---

## 14. 금지 표현

다음 표현을 그대로 사용하지 않습니다.

> 적당히 · 자연스럽게 · 재미있게 · 빠르게 · 강력하게 · 적절하게 · 다양한 · 어느 정도 · 상황에 따라

구체적인 기준이 필요하면 질문합니다. 질문할 수 없으면 `가정`으로 명시하고 진행합니다.

---

## 15. 기획 변경 방법

전체 문서를 다시 쓰지 않습니다. 변경된 시스템과 영향받는 시스템만 정리합니다.

```markdown
### 변경
기존: 초기 손패 7장
변경: 초기 손패 5장

### 영향
- 덱 시스템 (초기 지급 수)
- 승리 조건 (찹츄 10장까지 필요 드로우 수)
- 카드 밸런스
```

변경 시 **문서 하단 변경 이력에 날짜와 함께 기록**합니다.

---

## 16. 문서 가독성

* 긴 문단 대신 제목 / 소제목 / 표 / 번호 목록 / 상태 전이 / 조건·결과 표를 사용합니다.
* 한 문단에 여러 시스템 내용을 섞지 않습니다.
* 하나의 표에 너무 많은 정보를 넣지 않습니다.

---

## 17. 문서 상단 배치 순서

각 시스템 문서는 다음 순서로 시작합니다.

1. 목적
2. 분류 (Core/MVP/Optional/Future)
3. 핵심 규칙
4. 주요 수치
5. 입력
6. 상태 / 핵심 흐름
7. (그 아래) 상세 설명
8. (마지막) 예외 · 현재 구현 상태 · 미정 목록

---

## 18. 코드 작성 전

사용자가 단순히 기획을 요청했다면 **코드를 작성하지 않습니다.**

구현 요청이 오면 다음 순서로 진행합니다.

1. 필요한 시스템
2. 필요한 데이터
3. 기존 프로젝트에서 재사용할 부분
4. 구현 순서
5. 코드

---

## 19. 최종 목표

이 문서들은 "읽기 좋은 기획서"가 목적이 아닙니다.

**기획 → 시스템 설계 → Unity 구현 → 코드 작성**으로 바로 이어질 수 있는 개발 문서를 만드는 것이 목적입니다.

작성할 때마다 스스로 확인합니다.

> "이 문서를 받은 개발자가 이 기능을 어떻게 구현해야 하는지 충분히 알 수 있는가?"

알 수 없다면 더 구체적으로 작성합니다.

---

## 20. 이 프로젝트의 추가 규칙

1. **노션이 아니라 이 저장소가 기준이다.** 노션에서 결정된 내용은 `docs/systems/`에 반영해야 구현 대상이 된다.
2. 문서 최상단에 `분류`와 `최종 수정일`을 적는다.
3. 네트워크 게임이므로 모든 규칙에 **"누가 판정하는가"** 를 적는다 (마스터 / 각 클라이언트 / 해당 플레이어).
4. 카드 개별 효과는 `docs/systems/11-card-list.md` 한 곳에서만 관리한다. 시스템 문서에 카드 효과를 중복 기술하지 않는다.
