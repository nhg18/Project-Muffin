# 기획 문서 작성 지침

결과물: `docs/systems/*.md`. 목표는 개발자가 추가 질문 없이 구현을 시작할 수 있는 문서다.

## 1. 구체적으로

"무엇을"만이 아니라 **언제 · 누구에게 · 어떤 조건에서 · 어떤 결과**가 생기는지 쓴다.

| 나쁜 예 | 좋은 예 |
| --- | --- |
| 카드가 빠르게 날아간다 | 카드는 0.3초 동안 손패에서 가운데로 이동한다 |

금지 표현: 적당히 · 자연스럽게 · 재미있게 · 빠르게 · 적절하게 · 다양한 · 상황에 따라. 기준을 모르면 묻거나 `가정` 으로 쓴다.

## 2. 수치 표기

모든 규칙 · 수치에 표기를 붙인다.

| 표기 | 의미 | 구현 |
| --- | --- | --- |
| **확정** | 팀이 결정 | 구현한다 |
| **제안** | AI · 개인이 제시, 승인 필요 | 구현 전 확인 |
| **가정** | 임시 값 | 구현 전 확인 |
| **미정** | 결정 안 됨 | 구현하지 않는다 |

AI 가 정한 값은 반드시 `제안`.

## 3. 문서 구성

1. 머리말: `분류`(Core · MVP · Optional · Future) · `최종 수정일`
2. 목적 → 핵심 규칙 → 수치 → 입력 → 상태 · 흐름 → 상세 → 예외 → 미정 목록
3. 상태는 `현재 상태 | 조건 | 다음 상태 | 결과` 표, UI 는 `UI | 표시 조건 | 내용 | 동작` 표, 입력은 `입력 | 동작 | 조건` 표로.

## 4. 이 프로젝트 규칙

1. 노션이 아니라 이 저장소가 기준이다. 노션 결정은 `docs/systems/` 에 반영해야 구현 대상이 된다.
2. 모든 규칙에 **누가 판정하는가**(방장 / 각 클라이언트 / 해당 플레이어)를 적는다.
3. 비공개 정보(해당 플레이어에게만 보임)는 명시한다.
4. 카드 개별 효과는 `11-card-list.md` 에만 쓴다.
5. 기획서는 **되어야 할 상태**를 적는다. 클래스 · 메서드 · 파일 이름 같은 구현 위치는 적지 않고, "현재 구현" 을 근거로 쓰지 않는다. 코드가 다르면 코드를 고친다.
6. 바꿀 때는 해당 시스템과 영향받는 시스템만 고친다.
