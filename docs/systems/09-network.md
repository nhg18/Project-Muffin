## 1. 목적

"누가 무엇을 판정하고, 무엇을 어떻게 전파하는가"를 하나의 규칙으로 고정한다.
카드·체력·덱·턴 문서의 모든 규칙은 이 문서의 권한 모델 위에서 동작한다.

---

## 2. 핵심 규칙 (한 문장씩)

1. **게임 규칙 판정은 전부 마스터가 한다.** 클라이언트는 요청만 보낸다.
2. **원본 상태는 마스터 메모리에 하나만 존재한다.** 다른 클라이언트의 값은 전부 사본이다.
3. **클라이언트는 원본을 직접 수정하지 않는다.** 마스터의 브로드캐스트 결과만 반영한다.
4. **비공개 정보는 소유자에게만 보낸다.**
5. **연출은 로컬, 판정은 마스터.** 연출을 먼저 보여주고 결과가 다르면 되돌리는 방식(예측)은 MVP에서 쓰지 않는다.
6. **플레이어 식별자는 UGS 플레이어 ID 다.** 닉네임은 바꿀 수 있고 바꾼 이름은 남이 가져갈 수 있어(`23-login` 3절 #5) 식별에 쓰지 않고 표시용으로만 보낸다 (`23` 3절 #10, 확정 2026-11-07).

## 4. 요청-검증-전파 흐름

모든 플레이어 행동은 동일한 3단계를 거친다.

```
[클라이언트] 의도 전송 (Request)
      ↓ 믿는 방장에게 (13절 #1)
[마스터]     검증 (Validate)
      ↓ 실패 → 요청자에게만 거절 코드 전송 (4.3), 상태 변경 없음
      ↓ 성공
[마스터]     상태 변경 (Apply) — 마스터 메모리의 원본만 변경
      ↓ RpcTarget.All / 대상 지정
[전체]       결과 반영 + 연출
```

### 4.1 마스터가 검증하는 항목 (공통)

| 검증 | 실패 시 |
| --- | --- |
| 요청자가 실제로 그 카드를 소유하는가 (손패/함정 슬롯에 있는가) | 거절 |
| 요청 시점이 유효한가 (턴, 반응 시간 내, 메인 행동 미사용 등) | 거절 |
| 대상이 유효한가 (존재 · 생존 · 카드가 요구하는 조건) | 거절 |
| 카드의 사용 조건을 만족하는가 | 거절 |
| 이미 처리된 요청인가 (처리 ID 중복) | 무시 |

> 거절된 요청은 **상태를 전혀 변경하지 않는다.** 카드는 원래 위치를 유지한다.

### 4.2 동시 요청

* 함정 발동, 카운터 사용처럼 여러 명이 동시에 요청할 수 있는 행동은 **마스터 도착 순서로 1개만 승인**한다.
* 늦게 도착한 요청은 거절하고, 해당 카드는 원래 위치를 유지한다.
* 마스터는 승인 여부를 요청자에게 개별 응답한다.

## 5. 처리 ID (Resolve ID)

* 마스터는 보내는 **알림 1건마다** 1씩 늘어나는 **처리 번호**를 붙인다 (전원에게 가는 알림 · 한 사람에게 가는 알림 모두 같은 번호 줄). 카드 처리 1건에는 알림이 여럿이므로 카드마다가 아니라 알림마다 매긴다 (2026-11-06).
* 클라이언트는 마지막으로 받은 번호 **이하**를 받으면 무시한다 (중복 적용 방지). 같은 보낸이의 RPC 는 순서대로 오므로 번호는 늘기만 한다.
* 번호가 한 줄이라, 한 사람에게만 가는 알림은 다른 사람에게 번호의 빈칸으로 보인다. 빈칸이 숨긴 정보를 드러내면 그 알림은 **모두에게 하나씩** 보낸다 — 내용이 없는 사람에게는 빈 값 (3절 「낼 수 있는 내 카운터」, 2026-11-22 PM). 같은 사실을 전원 알림으로도 알리는 것(내 카드 뽑음 — 뽑았다는 사실은 전원 알림)은 빈칸이 드러내는 것이 없어 그대로 둔다.
* 지금 값 스냅샷(CustomProperties)에 그 스냅샷이 반영한 마지막 번호를 같이 둔다. 방장이 바뀌면 새 방장은 그 번호부터 잇는다 (게임 상태 이주는 9절). 재접속한 사람이 받는 전체 스냅샷(12절)도 이 번호를 달고 온다 — 그 뒤에 오는 알림만 반영한다.
* HP 변경 기록에도 처리 번호를 남긴다 (`06-health` 14절) — 기록의 보관 범위가 **미정**(06 18절 #2)이라 기록 자체는 아직 없다.

## 6. CustomProperties 사용 규칙

### 6.1 쓸 수 있는 것

* 모두가 항상 봐도 되는 **작은 값**: HP(int), 손패 장수(int), 함정 개수(int), 생존 상태(byte), 찹츄 상태(bool), 턴 주인(int), 턴 진행 방향(bool), 덱 · 버림 더미 장수(int), 버림 더미 맨 위 카드 종류 ID(int — 더미가 비면 키를 지운다, 2026-11-09)
* 늦게 들어온 클라이언트가 현재 상태를 복원해야 하는 값
* ~~**예외 — 이주용 큰 값 2개**~~ — 2026-11-19 폐기: 이주용 상태는 방 속성에 두지 않고 예비 방장에게만 보낸다 (9.1). 아래는 지난 방식의 기록이다: 덱 순서 · 버림 더미 순서(카드 인스턴스 ID 배열). 방장이 바뀌어도 게임을 이어 가기 위해 둔다 (9절, 2026-11-07). 카드가 덱에서 나가거나 버림 더미에 들어갈 때 마스터만 갱신한다. 클라이언트는 이 값을 **화면에 쓰지 않는다** — 덱 잔여 장수 · 버림 더미 표시는 지금처럼 장수 값 · 버림 이벤트로

> CustomProperties 는 **지금 값**이고, 연출 순서는 **일어난 일**(RPC)이 정한다.
> 게임 중 화면은 일어난 일을 차례로 재생하면서 값을 바꾼다. Props 가 바뀌었다고 바로 갱신하면 연출보다 숫자가 먼저 바뀐다 (예: 공격 연출 전에 HP 바가 줄어듦).

### 6.2 쓰면 안 되는 것

* 카드 ID **배열** 등 크기가 큰 값 (이주용 예외는 2026-11-19 폐기 — 9.1)
* 비공개 정보 (손패 내용, 함정 종류, 덱 순서) — 덱 순서는 다시 비공개다 (2026-11-19, 9.1)
* 프레임 단위로 바뀌는 값

## 7. 카드 인스턴스 ID

* 카드는 **종류 ID(`CardId`)** 와 **인스턴스 ID(`CardInstanceId`)** 를 구분한다.
* `CardId`: 카드 종류. `CardData.id`. 같은 카드는 값이 같다.
* `CardInstanceId`: 게임 시작 시 덱을 만들 때 카드 1장마다 부여하는 고유 번호. 게임 내내 유지된다.
* 클라이언트가 "이 카드를 쓰겠다"고 보낼 때는 **`CardInstanceId`** 를 보낸다.

**이유**: 같은 카드를 2장 들고 있을 때 `CardId`만으로는 어느 장인지 특정할 수 없다.
손패 훔치기(A04), 강제 버림(A05), 손패 교환(A11) 같은 카드는 인스턴스 단위 식별이 필수다.

## 8. 시간 동기화

* 반응 시간(5초 + 고민 연장)과 턴 제한 시간은 `PhotonNetwork.Time` (서버 시각) 기준으로 계산한다.
* 마스터는 "이 처리의 반응 마감 시각"을 절대 시각으로 브로드캐스트한다.
* 각 클라이언트는 남은 시간을 로컬에서 계산해 표시만 한다.
* **제한 시간 판정은 마스터만 한다.** 클라이언트 타이머가 0이 되어도 자체적으로 아무것도 확정하지 않는다.
* 마감 시각 이후 도착한 요청은 마스터가 거절한다.

### 9.1 이주 방식 — 예비 방장 (확정 PM 2026-11-19)

> 2026-11-07 의 방식(덱 순서는 방 속성 · 손패는 각자 다시 보냄 · 체인 불발 · 5초 대기)을 바꿨다. 그 방식은 각자가 손패를 거짓으로 신고할 수 있고, 덱 순서가 전원에게 보이며, 처리 중이던 카드가 사라졌다.

방장은 **예비 방장 한 명**에게만 게임 상태 전체의 사본을 계속 보내 둔다. 방장이 사라지면 예비 방장이 그 사본으로 판을 되살려 **멈췄던 단계부터 이어 간다**.

| # | 규칙 | 구분 |
| --- | --- | --- |
| 1 | **예비 방장** = 방장이 사라지면 Photon 이 방장으로 세울 사람 — 방에 남은 사람 중 번호(actorNumber)가 가장 작은 사람. 봇은 아니다 | 확정 (2026-11-19) |
| 2 | **사본** = 방장 메모리의 게임 상태 전체 — 덱 · 버림 더미 순서, 모든 사람(봇 포함)의 손패 · 함정 내용, HP · 상태, 턴, 처리 체인 · 반응 시간(스킵 · 고민 연장 기록 포함), 고르기, 사망 대기, 개판 · 대폭발 · 기다려, 지표. 카드는 인스턴스 ID 로 | 확정 (2026-11-19) |
| 3 | 방장은 상태가 바뀔 때마다(알림 묶음마다 · 알림이 없는 스킵 · 고민 연장도) 사본을 **예비 방장에게만** 대상 지정 RPC 로 보낸다. 방 속성에는 두지 않는다. 예비 방장이 나가면 그다음 사람에게 사본을 보낸다 | 확정 (2026-11-19) |
| 4 | 예비 방장의 기기는 사본을 **화면에 쓰지 않는다** — 받아 두기만 한다. 사본을 받는다는 표시도 없다 | 확정 (2026-11-19) |
| 5 | 새 방장은 사본으로 바로 되살린다 — 각자 손패를 다시 보내는 단계 · 대기 시간이 없다. 봇의 손패 · 함정도 그대로다 | 확정 (2026-11-19) |
| 6 | **이어 가기** — 카드를 냈거나 체인 · 고르기 도중이었어도 되돌리지 않고 그 단계부터 판정을 잇는다 | 확정 (2026-11-19) |
| 7 | **시간은 처음부터** — 멈췄던 단계의 시간을 새로 준다: 턴 15초 · 반응 시간 5초 · 고르기(카드의 시간) · 개판 판정 공개 (사망 대기에는 시간이 없다 — `06` 8절, 2026-11-22). 반응 시간에 이미 스킵한 사람의 스킵은 유지한다. 대폭발의 「이 턴 끝에 새 판」 예약도 유지한다 | 확정 (2026-11-19) |
| 8 | 새 방장은 되살린 직후 **덱을 다시 섞는다** — 예비 방장일 때 받은 덱 순서를 쓰지 못하게. 화면에는 아무것도 알리지 않는다 (덱 장수는 그대로) | 확정 (2026-11-19) |
| 9 | 새 방장은 사본 뒤에 나간 사람(앞 방장 포함)을 나감 처리하고, 각자에게 손패 · 함정 내용을 다시 보낸다 (10절 내 카드 다시 받기와 같은 알림) — 사본이 마지막 알림보다 한 걸음 늦었을 수 있다 | 확정 (2026-11-19) |
| 10 | **표시** — 모든 화면의 기록 서랍에 「방장이 바뀌었어요」 한 줄. 팝업은 없다 | 확정 (2026-11-19) |
| 11 | **이주 실패** — 새 방장에게 사본이 없거나(방장과 예비 방장이 함께 사라짐) 읽을 수 없으면 게임을 중지하고 **전원이 방(대기 화면)으로 돌아간다**. 방은 다시 열리고 거기서 다시 시작할 수 있다. 도착하면 경고 팝업 「게임을 이어갈 수 없어 방으로 돌아왔어요」 (`22-popup-ui`). 이 **중지 알림은 처리 번호(5절)로 거르지 않고** 믿는 방장이 보냈는지만 본다 — 사본이 없는 새 방장은 앞 방장이 각자에게 몇 번까지 보냈는지 몰라 번호가 겹칠 수 있고, 판의 마지막 알림이라 다시 받아도 결과가 같다 | 확정 (2026-11-19) / 제안 (번호로 거르지 않기 — 리뷰 2026-11-20) |

흐름:

1. Photon 이 새 마스터를 승격한다 → 모든 클라이언트가 `OnMasterClientSwitched` 를 받는다. 앞 방장이 방에 그대로 있으면 받아들이지 않는다 (13절 #1).
2. 새 방장은 받아 둔 사본으로 게임 상태를 되살리고, 처리 번호를 잇는다 (5절 — 사본에 방장이 마지막으로 보낸 번호가 함께 온다).
3. 덱을 다시 섞고, 멈췄던 단계의 시간을 새로 주어 알린다 (턴 재개 · 고르기 알림을 다시 보낸다).
4. 나간 사람을 처리하고, 각자에게 손패 · 함정을 다시 보낸다. 그 뒤로는 새 방장이 다음 사람에게 사본을 보낸다.

> **한계** — 방장이 알림을 보낸 직후, 그 사본이 나가기 전에 사라지면 사본이 한 걸음 늦다. 그때는 마지막 알림 하나가 새 방장의 판에 없다 (화면에는 보였던 일이 없던 일이 된다). 알림과 사본을 같은 묶음으로 내보내 이 틈을 줄인다.
> 끝난 판(종료 알림 뒤)은 이주하지 않는다 — 새 방장이 결과 씬으로 옮기기만 한다.
>
> 지킬 것: 마스터의 게임 상태를 한 곳에 모아 통째로 넘길 수 있게 둔다 (`CODE_CONVENTION` 9절). 원본 상태를 더하면 사본에도 더한다 — `rules` 의 방장 이주 시나리오가 되살린 상태를 필드마다 견준다.

| 마스터 전용 RPC | 첫 줄에 `if (!NetworkManager.IsTrustedMaster) return;` — 내가 **믿는 방장**(13절 #1)일 때만 (`PhotonNetwork.IsMasterClient` 가 아니라). 요청 RPC 는 둘째 줄에 보낸 사람별 빈도 제한 (13절 #6) |
| 요청 보내기 | 믿는 방장 Player 에게 대상 지정으로 보낸다 (`RpcTarget.MasterClient` 가 아니라, 13절 #1) |
| 결과 RPC 받기 | **믿는 방장**(13절 #1)이 보낸 것만 반영한다. 짝 배열(인스턴스 ID · 카드 ID 등)은 길이가 같아야 받는다 (13절 #7) |
| 요청자 식별 | `PhotonMessageInfo.Sender` 사용. 클라이언트가 보낸 actorNumber를 신뢰하지 않는다 |
| 명명 | 요청은 `RPC_Request*`, 결과 전파는 `RPC_On*`, 개별 응답은 `RPC_Reject*` |
| 처리 번호 | 결과 전파 · 개별 응답 RPC 는 첫 인자가 처리 번호 (5절) |
| 내 카드 다시 받기 | 화면이 늦게 열렸거나 다시 그릴 때 클라가 요청하면, 마스터가 그 사람의 손패 · 설치 함정 내용을 지금 처리 번호로 그 사람에게만 보낸다. 공개 값은 스냅샷(6절)에서 읽는다 (2026-11-06) |
| 전체 복원 (재접속) | 「내 카드 다시 받기」 의 확장. 끊겼다 돌아온 사람에게 마스터가 **전체 스냅샷**(좌석 · 손패 · 함정 내용 · 전원 HP · 생존 · 찹츄 · 턴 주인 · 진행 방향 · 체인 상태 · 반응 시작 · 턴 마감 시각 · 덱 장수)을 처리 번호와 함께 그 사람에게만 보낸다 (12절, 2026-11-07) |
| 대상이 고르는 효과 (1019) | 방장이 `RPC_OnChoiceStarted`(고르는 사람 · 쓴 사람 · 카드 · 손패 장수 · 피해 · 시작 · 마감 시각)를 **전원**에게 보내고, 고르는 사람이 `RPC_RequestChoose(option, deadline)` 으로 요청한다(요청자는 `Sender`). `deadline` 은 답하는 고르기의 마감 — `RPC_OnChoiceStarted` 로 받은 값을 그대로 되돌려 보낸다 (2026-11-27, 리뷰 지적). 방장이 시간 · 고르는 사람 · **그 마감이 지금 열린 고르기의 것인지**를 판정하고 — 같은 고르기를 연달아 열 때(2배가 된 2021 으르렁의 대가 2장) 앞 고르기가 시간 초과로 끝난 뒤 도착한 요청을 다음 고르기의 답으로 받지 않는다 (코드 20) — `RPC_OnChoiceMade`(고르는 사람 · 고른 것(0 버리기 · 1 피해 · −1 나가서 불발) · 시간 초과)를 전원에게. 시간 초과면 방장이 무작위로 (2026-11-13) |
| 반응 시간 스킵 · 고민 연장 | 스킵 = `RPC_RequestReactionSkip()`, 고민 = `RPC_RequestReactionHold(cardInstanceId)` (요청자는 `Sender`). 방장이 반응 시간 중인지 · 요청자가 물어야 할 사람인지 (고민은 그 카드가 그 사람의 낼 수 있는 목록에 있는지 · 이번 반응 시간에 아직 늘리지 않았는지) 를 보고 처리한다. **둘 다 결과를 전파하지 않고, 거절해도 알리지 않는다** — 모두 스킵하면 체인 처리가 시작되는 것으로만 드러난다 (`04-card` 8절, 2026-11-15) |
| 게임 종료 → 결과 화면 (`07` 11-1) | 방장이 `RPC_OnGameEnded`(승자 · 승리 방식 + 순위 순 배열: 접속 번호 · 순위 · 최종 HP · 빠진 턴 · 당한 사람 · 나감 + **판 지표**(사람마다 12개를 순위 순으로 이어 붙인 정수 배열, `07` 11-4) · **끝난 턴 번호**, 2026-11-18)를 **전원**에게 보내고, 같은 때 결과 화면 상태(마감 시각 · 준비 · 카운트다운 지움)를 방 속성에 쓴다. 2초 뒤 공개 값(HP · 손패 장수 · 턴 주인 · 처리 번호 등 — 봇 키 포함)을 시작 값으로 되돌리고 전원을 결과 씬으로 옮긴다 (13절 #5). 그 사이 방장이 바뀌면 새 믿는 방장이 이어서 한다. 게임이 끝난 뒤 클라는 게임 요청을 보내지 않는다 (2026-11-17) |
| 결과 화면의 요청 (`07` 11-1) | 결과 씬의 PhotonView(`PunResultServer` — 씬 뷰 ID **2**, 게임 씬의 1 과 겹치지 않게)가 맡는다. 준비 · 취소 = `RPC_ResultRequestSetReady(ready)` (요청자는 `Sender`). 방장이 준비한 사람 · 카운트다운 끝 시각을 방 속성에 쓰고 화면은 그 값을 그린다 — 준비에는 결과 RPC 가 없다. 이모트 = `RPC_ResultRequestEmote(번호)` → 방장이 번호(0 ~ 3) · 보낸 사람이 방에 있는지 · 빈도(13절 #6 에 더해 사람마다 1초에 한 번)를 보고 `RPC_OnResultEmote(접속 번호, 번호)` 를 전원에게 보낸다. 받는 쪽은 믿는 방장이 보낸 것만 받고 번호 범위를 다시 본다. 말은 번호로만 오간다 — 글자를 보내지 않는다 (`07` 11-2, 2026-11-18). 봇 준비 · 전원 준비 판정 · 다음 판 시작은 방장. 자동 이동은 각 클라가 스스로 방을 나간다 (2026-11-17) |
| 방장이 쓴 방 속성 읽기 | 방장은 자기가 쓴 속성을 서버가 되돌려 준 뒤에야 방에서 본다. 방장이 쓰고 곧바로 읽어야 하는 값(결과 화면 상태)은 `NetworkManager.RoomProp(key)` 로 읽는다 — 방장은 기억해 둔 원본(13절 #2), 남은 방의 값 (2026-11-17) |
| ~~손패 · 함정 다시 보내기 (이주)~~ | ~~마스터가 바뀌면 각 클라이언트가 자기 손패 · 함정 내용을 새 마스터에게 보낸다~~ — 2026-11-19 폐기: 새 방장은 사본으로 되살리고, 반대로 각자에게 손패 · 함정을 다시 보낸다 (9.1 #5 · #9) |

| 끊긴 사람이 HP 0 | 사망 정리를 그대로 한다 — 사망 대기에는 입력이 없다 (`06` 8절) | 확정 (기존 규칙) |
| 끊긴 사람 둘 이상 | 각각 #3 · #4 | 확정 |

| 복원 요청 뒤 5초 안에 스냅샷이 안 옴 | 다시 요청. 3회 실패하면 방을 나가 로비로 | 제안 |

## 13. 클라 변조 대비 (2026-11-15)

Photon 은 **아무 클라나** 방 속성 · 남의 Player 속성 · 방 설정(열림 · 공개 · 정원 · TTL) · 방장 자리(`SetMasterClient`)를 바꿀 수 있게 둔다. PUN 은 남이 보낸 Destroy · Instantiate · 소유권 이벤트도 보낸 사람 확인 없이 처리한다. 서버 코드가 없으므로 클라가 지킨다. 근거: 외부 보안 검증 (2026-11-14, MU-03 · 06 · 09 · 10 · 12 · 13 · 15 · 19 · NEW-01 · 03 외).

| # | 규칙 | 구분 |
| --- | --- | --- |
| 1 | **믿는 방장** — 방에 들어올 때의 방장. 그 뒤엔 **방장이 나가서(또는 끊겨서)** 바뀐 사람만 믿는다. 앞 방장이 방에 그대로 있는데 방장이 바뀌면 누가 가져간 것이다 → 믿지 않고, 앞 방장 기기는 방장 자리를 되찾는다 (`SetMasterClient`). 요청은 믿는 방장에게 보내고, 방장 전용 경로(요청 받기 · 게임 진행 · 방장 원본 읽기)는 내가 믿는 방장인지로 판단한다 (`PhotonNetwork.IsMasterClient` 는 가져간 사람에게도 참). 결과 RPC · 씬 이동은 믿는 방장이 보낸 것만 따른다 | 확정 (2026-11-15) |
| 2 | **방장이 쓴 값 지키기** — 방장은 방 속성 · Player 속성 · 열림 · 공개 · 정원 · TTL 을 쓸 때 그 값을 기억한다. 남이 바꾸면 다음 프레임에 기억한 값으로 되돌린다 (방장이 쓴 적 없는 키는 지운다). 한 프레임에 여러 번 바뀌어도 한 번만 쓴다. 자리 예약(ExpectedUsers)은 쓰지 않으므로 생기면 지운다 | 확정 (2026-11-15) |
| 3 | 방장이 되면(정상 이주) 그때 방의 값을 원본으로 이어받는다. 봇 목록도 이것으로 지킨다 (`18-bot` 3절 #7). **게임 중**에는 방 속성이 아니라 이주 사본(9.1)으로 되살리고, 되살린 값을 방 속성에 다시 쓴다 — 앞 방장이 사라진 틈에 남이 바꾼 방 속성을 원본으로 받지 않게 | 확정 (2026-11-15) / 확정 (게임 중 사본, 2026-11-19) |
| 4 | **내 이름** — 남이 내 닉네임 속성을 바꾸면 각자 자기 이름을 되돌린다 (방장이 아니어도) | 확정 (2026-11-15) |
| 5 | **씬 이동** — PUN 씬 동기화(`AutomaticallySyncScene`)를 쓰지 않는다 (방 속성 `curScn` 을 누가 썼는지 보지 않는다). 방장이 방 전원에게 「이 씬으로」 이벤트를 보내고, 받는 쪽은 믿는 방장이 보냈고 방 · 게임 · 결과 씬일 때만 따른다 (결과 씬 추가 2026-11-17). 방에 들어온 사람은 각자 로비가 방 씬을 연다 | 확정 (2026-11-15) |
| 6 | **요청 빈도** — 방장은 보낸 사람마다 요청을 **10개까지 몰아서, 그 뒤엔 초당 5개**까지 받는다. 넘친 요청은 답 없이 버린다. 거절만 일어난 요청은 지금 값 스냅샷(6절)을 다시 쓰지 않는다 | 확정 (2026-11-15) / 값 10 · 5 는 제안 |
| 7 | **결과 모양** — 짝 배열은 길이가 같아야 받고, 빈 배열 대신 null 이 오면 빈 배열로 읽는다. 화면 연출 큐는 한 단계가 예외를 내면 그 단계만 버리고 다음으로 간다 | 확정 (2026-11-15) |
| 8 | **속성 읽기** — 화면이 속성에서 읽는 값은 남이 잠깐 바꿨을 수 있다(#2 가 되돌리기 전). HP 는 0 ~ 최대로, 「기다려」 건 사람은 판에 있는 사람만 · 겹치지 않게, 상대가 좌석 수보다 많으면 앉힐 수 있는 만큼만. 결과 화면의 자동 이동 마감은 「내 화면이 열린 시각 + 45초」 에서 10초 앞까지만 받아들인다 — 남이 0 으로 바꿔 방을 비우거나 크게 바꿔 붙잡아 두지 못하게 (2026-11-17, 10초는 제안) | 확정 (2026-11-15) |
| 9 | **시작 인원** — 방장은 게임 시작 때 사람 + 봇이 2 ~ 4 명인지 다시 본다. 아니면 시작하지 않고 방을 열어 전원을 방으로 돌린다 (정원은 #2 가 지키지만 그 사이에 들어올 수 있다) | 확정 (2026-11-15) |
| 10 | **PUN 이벤트** — 이 게임은 RPC 만 쓴다. Destroy · Instantiate · 소유권 · 직렬화 · 추방(CloseConnection) 이벤트는 받지 않는다. 내보내기(`08-room` 5절 #9)를 만들 때는 이 이벤트 대신 믿는 방장만 보낼 수 있는 자기 이벤트로 | 확정 (2026-11-15) |
| 11 | **처리 번호** — 새 방장이 방 속성의 처리 번호(5절)를 이어받을 때, 받은 번호보다 **1000** 넘게 크면 쓰지 않는다 (남이 큰 값을 써 새 방장의 알림을 전부 묵은 것으로 만들지 못하게) | 확정 (2026-11-15) / 값 1000 은 제안 |
| 12 | **난수** — 덱 섞기 · 무작위 판정 · 방 코드는 암호 난수로 (시드로 다음 값을 맞추지 못하게) | 확정 (2026-11-15) |
| 12-1 | **카드 데이터** — 같은 방은 같은 카드다. 카드는 빌드에 들어 있고, 접속 버전(앱 버전)이 같은 사람끼리만 만나기 때문이다 ([`../versioning.md`](../versioning.md) · `26-card-data` 3절 #9). 방 속성으로 따로 가르지 않는다 | 확정 (2026-11-20 PM) |
| 12-2 | **이주 사본** — 사본(9.1)은 믿는 방장이 보낸 것만 받고, 크기 한도를 넘으면 받지 않는다. 읽다가 모자라거나 남거나 이 덱에 없는 카드가 나오면 되살리지 않고 판을 중지한다 (9.1 #11). 사본은 한 명에게만 가므로 덱 순서 · 남의 손패가 전원에게 보이지 않는다 | 확정 (2026-11-19) |
| 13 | **비공개 정보 로그** — 손패 · 함정 내용은 개발 빌드 로그에만 남긴다 (`CODE_CONVENTION` 7절) | 확정 (2026-11-15) |

> **여기서 못 막는 것** — 방장 기기 자체를 고친 사람(카드 값 · 판정 · 가짜 결과)은 막을 수 없다. 예비 방장 기기를 고친 사람은 사본(덱 순서 · 남의 손패 · 함정)을 볼 수 있고, 방장이 된 뒤에는 방장과 같다 (9.1). 방장 권한 구조의 한계다 (근본 대책 = 판정을 서버로). Photon 앱 ID 는 공개 저장소에 있어 누구나 접속할 수 있고, 플레이어 식별자(2절 #6)는 토큰 확인 없이 클라가 정한다 — Photon **Custom Authentication**(UGS 토큰 확인 서버)이 있어야 막힌다. 닉네임 정책(`23-login` 8-3)도 서버(Cloud Code)가 있어야 강제된다.
>
> 지킬 것: 방장의 속성 쓰기는 모두 `NetworkManager.SetRoomProps` · `SetPlayerProps` · `UpdateRoomOptions` 로 한다 — `SetCustomProperties` 를 직접 부르면 #2 가 그 값을 남이 쓴 것으로 보고 지운다. 플레이어가 **자기** 속성에 쓰는 키(3절 「플레이어 식별자」)를 만들면 #2 의 예외로 넣는다.
