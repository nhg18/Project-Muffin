# 09. 네트워크 권한 · 동기화 규약

**최종 수정일**: 2026-11-07
**분류**: Core
**전제**: Photon PUN2. 마스터 클라이언트(방장)가 서버 역할을 겸한다. 계정 · 저장(UGS)은 [`23-login.md`](23-login.md) — 이 문서는 방 · 게임 안의 동기화만. 플레이어 식별자는 UGS 플레이어 ID (2절 #6).

---

## 1. 목적

"누가 무엇을 판정하고, 무엇을 어떻게 전파하는가"를 하나의 규칙으로 고정한다.
카드·체력·덱·턴 문서의 모든 규칙은 이 문서의 권한 모델 위에서 동작한다.

---

## 2. 핵심 규칙 (한 문장씩)

1. **게임 규칙 판정은 전부 마스터가 한다.** 클라이언트는 요청만 보낸다.
2. **원본 상태는 마스터 메모리에 하나만 존재한다.** 다른 클라이언트의 값은 전부 사본이다.
3. **클라이언트는 원본을 직접 수정하지 않는다.** 마스터의 브로드캐스트 결과만 반영한다.
4. **비공개 정보는 소유자에게만 보낸다.**
5. **연출은 로컬, 판정은 마스터.** 연출을 먼저 보여주고 결과가 다르면 되돌리는 방식(예측)은 MVP에서 쓰지 않는다.
6. **플레이어 식별자는 UGS 플레이어 ID 다.** 닉네임은 중복 허용(`23-login` 3절 #5)이라 식별에 쓰지 않고 표시용으로만 보낸다 (`23` 3절 #10, 확정 2026-11-07).

## 3. 권한 표 (Authority Matrix)

| 데이터 | 원본 소유 | 공개 범위 | 전송 방식 |
| --- | --- | --- | --- |
| 덱 (남은 카드 목록·순서) | 마스터 | **화면에는 그리지 않는다** — 데이터는 전체에 전송됨 (방장 교체 이주를 위해 노출을 감수, 9절) | Room CustomProperties — 마스터만 쓴다 (2026-11-07) |
| 덱 잔여 장수 | 마스터 | 전체 공개 | Room CustomProperties |
| 버림 더미 (내용 · 순서) | 마스터 | 전체 공개 | 카드가 버려질 때 이벤트로 전파 (사망 · 나감도 버려진 카드 ID 배열을 싣는다, 2026-11-09) + 순서 전체를 Room CustomProperties 에 (이주용, 9절 · 2026-11-07) |
| 버림 더미 장수 · 맨 위 카드 | 마스터 | 전체 공개 | Room CustomProperties — 늦게 열린 화면의 복구용 (2026-11-09) |
| 손패 **내용** | 마스터 | **소유자만** | 소유자 지정 RPC |
| 손패 **장수** | 마스터 | 전체 공개 | Player CustomProperties |
| 함정 슬롯 **내용** | 마스터 | **소유자만** | 소유자 지정 RPC |

| 함정 슬롯 **개수** | 마스터 | 전체 공개 | Player CustomProperties |
| HP | 마스터 | 전체 공개 | Player CustomProperties |
| 생존 상태 (Alive/DeathPending/Dead) | 마스터 | 전체 공개 | Player CustomProperties |
| 찹츄 상태 | 마스터 | 전체 공개 | Player CustomProperties |
| 현재 턴 주인 | 마스터 | 전체 공개 | Room CustomProperties |
| 턴 진행 방향 (정 / 역) | 마스터 | 전체 공개 | Room CustomProperties — 턴 주인과 같은 취급 (`03-turn` 6절 #4, 2026-11-07) |
| 처리 체인 | 마스터 | 전체 공개 | 체인 변화 시 RPC 브로드캐스트 |
| 반응 타이머 시작 · 마감 시각 | 마스터 | 전체 공개 | RPC(`PhotonNetwork.Time` 기준). 연출 시간을 더한 절대 시각 (`04-card` 8절) |
| 좌석 배치 | **각 클라이언트 로컬 계산** | 로컬 | 전송 안 함 (`02-player` 참고) |
| 손패 이동 (훔치기 · 교환 · 반환) | 마스터 | 장수는 전체, **어떤 카드인지는 주고받은 두 사람만** | 전원에게 장수 RPC + 두 사람에게 카드 RPC (2026-11-06) |
| 강제 버림 · 함정 파괴 | 마스터 | 전체 공개 (버림 더미로 가므로) | RPC (카드 ID 포함) |
| 함정 반환 · 빼앗기 | 마스터 | 개수는 전체, 종류는 관련된 사람만 (반환 = 주인, 빼앗기 = 두 사람) | RPC |
| 봇 목록 (번호) | 방장 | 전체 공개 | Room CustomProperties (`18-bot` 9절) |
| 봇의 공개 값 (HP · 손패 장수 · 함정 개수 · 생존 · 찹츄) | 마스터 | 전체 공개 | Room CustomProperties — 사람과 같은 키 + `#봇 식별자` (`18-bot` 9절) |
| 봇의 손패 · 함정 내용 | 마스터 | **아무에게도** | 전송 안 함 — 방장 화면에도 그리지 않는다 (`18-bot` 3절 #5) |
| 카드 호버/드래그/연출 | 각 클라이언트 | 로컬 | 전송 안 함 |
| 플레이어 식별자 (UGS 플레이어 ID) | 해당 플레이어 (계정, `23-login`) | 전체 공개 | 방 입장 때 자기 Player CustomProperties 에 1회 — 확정 (식별자 = UGS 플레이어 ID, 2026-11-07) / 제안 (전송 방식). 닉네임은 표시용 |

## 4. 요청-검증-전파 흐름

모든 플레이어 행동은 동일한 3단계를 거친다.

```
[클라이언트] 의도 전송 (Request)
      ↓ RpcTarget.MasterClient
[마스터]     검증 (Validate)
      ↓ 실패 → 요청자에게만 거절 코드 전송 (4.3), 상태 변경 없음
      ↓ 성공
[마스터]     상태 변경 (Apply) — 마스터 메모리의 원본만 변경
      ↓ RpcTarget.All / 대상 지정
[전체]       결과 반영 + 연출
```

### 4.1 마스터가 검증하는 항목 (공통)

| 검증 | 실패 시 |
| --- | --- |
| 요청자가 실제로 그 카드를 소유하는가 (손패/함정 슬롯에 있는가) | 거절 |
| 요청 시점이 유효한가 (턴, 반응 시간 내, 메인 행동 미사용 등) | 거절 |
| 대상이 유효한가 (존재 · 생존 · 카드가 요구하는 조건) | 거절 |
| 카드의 사용 조건을 만족하는가 | 거절 |
| 이미 처리된 요청인가 (처리 ID 중복) | 무시 |

> 거절된 요청은 **상태를 전혀 변경하지 않는다.** 카드는 원래 위치를 유지한다.

### 4.2 동시 요청

* 함정 발동, 카운터 사용처럼 여러 명이 동시에 요청할 수 있는 행동은 **마스터 도착 순서로 1개만 승인**한다.
* 늦게 도착한 요청은 거절하고, 해당 카드는 원래 위치를 유지한다.
* 마스터는 승인 여부를 요청자에게 개별 응답한다.

---

### 4.3 거절 코드

* 방장은 거절 **문구가 아니라 코드(`int`)** 만 요청자에게 보낸다. 화면 문구는 클라이언트(UI)가 코드로 정한다 — [`10-ui.md`](10-ui.md) 8-2.

## 5. 처리 ID (Resolve ID)

* 마스터는 보내는 **알림 1건마다** 1씩 늘어나는 **처리 번호**를 붙인다 (전원에게 가는 알림 · 한 사람에게 가는 알림 모두 같은 번호 줄). 카드 처리 1건에는 알림이 여럿이므로 카드마다가 아니라 알림마다 매긴다 (2026-11-06).
* 클라이언트는 마지막으로 받은 번호 **이하**를 받으면 무시한다 (중복 적용 방지). 같은 보낸이의 RPC 는 순서대로 오므로 번호는 늘기만 한다.
* 지금 값 스냅샷(CustomProperties)에 그 스냅샷이 반영한 마지막 번호를 같이 둔다. 방장이 바뀌면 새 방장은 그 번호부터 잇는다 (게임 상태 이주는 9절). 재접속한 사람이 받는 전체 스냅샷(12절)도 이 번호를 달고 온다 — 그 뒤에 오는 알림만 반영한다.
* HP 변경 기록에도 처리 번호를 남긴다 (`06-health` 14절) — 기록의 보관 범위가 **미정**(06 18절 #2)이라 기록 자체는 아직 없다.

## 6. CustomProperties 사용 규칙

### 6.1 쓸 수 있는 것

* 모두가 항상 봐도 되는 **작은 값**: HP(int), 손패 장수(int), 함정 개수(int), 생존 상태(byte), 찹츄 상태(bool), 턴 주인(int), 턴 진행 방향(bool), 덱 · 버림 더미 장수(int), 버림 더미 맨 위 카드 종류 ID(int — 더미가 비면 키를 지운다, 2026-11-09)
* 늦게 들어온 클라이언트가 현재 상태를 복원해야 하는 값
* **예외 — 이주용 큰 값 2개**: 덱 순서 · 버림 더미 순서(카드 인스턴스 ID 배열). 방장이 바뀌어도 게임을 이어 가기 위해 둔다 (9절, 2026-11-07). 카드가 덱에서 나가거나 버림 더미에 들어갈 때 마스터만 갱신한다. 클라이언트는 이 값을 **화면에 쓰지 않는다** — 덱 잔여 장수 · 버림 더미 표시는 지금처럼 장수 값 · 버림 이벤트로

> CustomProperties 는 **지금 값**이고, 연출 순서는 **일어난 일**(RPC)이 정한다.
> 게임 중 화면은 일어난 일을 차례로 재생하면서 값을 바꾼다. Props 가 바뀌었다고 바로 갱신하면 연출보다 숫자가 먼저 바뀐다 (예: 공격 연출 전에 HP 바가 줄어듦).

### 6.2 쓰면 안 되는 것

* 카드 ID **배열** 등 크기가 큰 값 — 6.1 의 이주용 2개만 예외
* 비공개 정보 (손패 내용, 함정 종류) — 덱 순서는 「비공개」 에서 빼기로 했다 (2026-11-07, 3절)
* 프레임 단위로 바뀌는 값

### 6.3 키 상수

문자열 리터럴 금지. 상수 클래스에 모은다.

```csharp
public static class PlayerProps
{
    public const string Hp        = "hp";
    public const string HandCount = "handCount";
    public const string TrapCount = "trapCount";
    public const string LifeState = "lifeState";
    public const string ChapChu   = "chapChu";
    public const string ActionBlock = "actionBlock"; // 행동 카드 금지 (byte: 1 다음 턴 · 2 이번 턴, 107). 없으면 키 없음 (2026-11-13)
}

public static class RoomProps
{
    public const string TurnActor    = "turnActor";
    public const string DeckCount    = "deckCount";
    public const string DiscardCount = "discardCount";
    public const string DiscardTop   = "discardTop"; // 맨 위 카드 종류 ID. 더미가 비면 키 없음 (2026-11-09)
    public const string TurnDirection = "turnDir";
    public const string WaitCasters  = "wait";     // 「기다려」 를 건 사람들 (int[], 123). 없으면 키 없음 (2026-11-13)
    public const string DeckOrder    = "deck";     // 이주용 (6.1 예외, 2026-11-07)
    public const string DiscardOrder = "discard";  // 이주용
}
```

## 7. 카드 인스턴스 ID

* 카드는 **종류 ID(`CardId`)** 와 **인스턴스 ID(`CardInstanceId`)** 를 구분한다.
* `CardId`: 카드 종류. `CardData.id`. 같은 카드는 값이 같다.
* `CardInstanceId`: 게임 시작 시 덱을 만들 때 카드 1장마다 부여하는 고유 번호. 게임 내내 유지된다.
* 클라이언트가 "이 카드를 쓰겠다"고 보낼 때는 **`CardInstanceId`** 를 보낸다.

**이유**: 같은 카드를 2장 들고 있을 때 `CardId`만으로는 어느 장인지 특정할 수 없다.
손패 훔치기(A04), 강제 버림(A05), 손패 교환(A11) 같은 카드는 인스턴스 단위 식별이 필수다.

## 8. 시간 동기화

* 반응 시간(10초)과 턴 제한 시간은 `PhotonNetwork.Time` (서버 시각) 기준으로 계산한다.
* 마스터는 "이 처리의 반응 마감 시각"을 절대 시각으로 브로드캐스트한다.
* 각 클라이언트는 남은 시간을 로컬에서 계산해 표시만 한다.
* **제한 시간 판정은 마스터만 한다.** 클라이언트 타이머가 0이 되어도 자체적으로 아무것도 확정하지 않는다.
* 마감 시각 이후 도착한 요청은 마스터가 거절한다.

## 9. 마스터 클라이언트 이전

| 상황 | 처리 | 구분 |
| --- | --- | --- |
| 마스터가 나감 (연결 끊김 포함) | Photon이 다음 클라이언트를 마스터로 승격 | 확정(Photon 동작) |
| 승격된 새 마스터가 게임 상태를 복원 | **이주** — 게임을 끝내지 않고 새 마스터가 이어받는다. 방식은 아래 9.1 | 확정 (방향 2026-10-30 · 방식 2026-11-07) |

"마스터가 나가면 게임 종료" 안은 채택하지 않았다 (2026-10-30, 유지). 구현은 `development-plan` 기능 11.

### 9.1 이주 방식 (확정 2026-11-07)

마스터 메모리에만 있던 것을 **세 갈래**로 되살린다. 덱 순서가 클라이언트에 노출되는 것은 감수한다 — 친구끼리 하는 파티 게임이다.

| 상태 | 어디서 되살리나 | 누가 보내나 | 구분 |
| --- | --- | --- | --- |
| 덱 순서 · 버림 더미 순서 | **Room CustomProperties** (6.1 예외) — 늘 최신으로 두므로 새 마스터는 읽기만 | (이미 있음) | 확정 (2026-11-07) |
| 공개 값 (HP · 손패 장수 · 함정 개수 · 생존 · 찹츄 · 행동 금지 · 턴 주인 · 방향 · 기다려 · 덱 장수 · 처리 번호) | Player · Room CustomProperties 스냅샷 (6절) | (이미 있음) | 확정 (기존) |
| **손패 내용** | 각 클라이언트가 **자기 손패**(카드 인스턴스 ID 목록)를 새 마스터에게 다시 보낸다 | 각 클라이언트 → 새 마스터 (소유자 지정 RPC) | 확정 (2026-11-07) |
| **함정 슬롯 내용** | 소유자가 **자기 함정**(인스턴스 ID · 슬롯 순서)을 다시 보낸다 | 소유자 → 새 마스터 | 확정 (2026-11-07) |
| 처리 체인 · 반응 타이머 | 복원하지 않는다 — 진행 중이던 체인은 **불발**로 끝내고(카드는 버림 더미로), 턴은 지금 턴 주인의 턴 종료로 넘긴다 | 새 마스터가 판정 | 확정 (2026-11-07) |
| 봇 (`18-bot`) | 봇의 손패 · 함정은 아무에게도 없었으므로(3절) 새 마스터가 **손패 장수만큼 덱에서 새로 뽑아** 채우고, 함정은 개수만큼 버린 것으로 본다(슬롯 비움) | 새 마스터 | 확정 (2026-11-07) |

흐름:

1. Photon 이 새 마스터를 승격한다 → 모든 클라이언트가 `OnMasterClientSwitched` 를 받는다.
2. 새 마스터는 Room · Player CustomProperties 스냅샷으로 공개 상태 · 덱 · 버림 더미를 만들고, 처리 번호를 스냅샷 번호부터 잇는다 (5절).
3. 각 클라이언트(새 마스터 자신 포함)는 자기 손패 · 함정 내용을 새 마스터에게 보낸다.
4. 새 마스터는 받은 손패 장수가 Player CustomProperties 의 장수와 **다르면** 그 사람의 값을 신뢰하지 않고 **장수만큼 덱 위에서 다시 준다** (사본 유실 · 조작 대비). 함정도 개수가 다르면 슬롯을 비운다.
5. 전원의 손패 · 함정이 모이면(또는 **5초**가 지나면) 게임을 이어 간다 — 그동안 요청은 `Resolving` 코드로 거절한다. 5초 확정 (2026-11-07).

> 새 마스터가 선 시점에 **연결이 끊겨 있던 사람**은 3 을 못 한다. 그 사람 손패는 4 의 규칙으로 돌아올 때 채운다 — 돌아온 뒤 자기 사본을 보내면 장수가 맞을 때만 받는다. 앱을 다시 켜서 사본이 없으면 덱에서 새로 받는다. (확정 2026-11-07, 13절 #4)
>
> 지킬 것: 마스터의 게임 상태를 한 곳에 모아 통째로 넘길 수 있게 둔다 (`CODE_CONVENTION` 9절).

## 10. RPC 규약

```csharp
// 클라이언트 → 마스터
photonView.RPC(nameof(RPC_RequestPlayCard), RpcTarget.MasterClient, cardInstanceId, targets);

// 마스터 → 전체
photonView.RPC(nameof(RPC_OnCardPlayed), RpcTarget.All, resolveId, actorNumber, cardId, targets);

// 마스터 → 특정 플레이어 (비공개 정보)
photonView.RPC(nameof(RPC_SyncMyHand), targetPlayer, cardInstanceIds, cardIds);
```

| 규칙 | 내용 |
| --- | --- |
| 메서드명 | `RPC_` 접두사 |
| 이름 전달 | `nameof()` 사용, 문자열 리터럴 금지 |
| 마스터 전용 RPC | 첫 줄에 `if (!PhotonNetwork.IsMasterClient) return;` |
| 요청자 식별 | `PhotonMessageInfo.Sender` 사용. 클라이언트가 보낸 actorNumber를 신뢰하지 않는다 |
| 명명 | 요청은 `RPC_Request*`, 결과 전파는 `RPC_On*`, 개별 응답은 `RPC_Reject*` |
| 처리 번호 | 결과 전파 · 개별 응답 RPC 는 첫 인자가 처리 번호 (5절) |
| 내 카드 다시 받기 | 화면이 늦게 열렸거나 다시 그릴 때 클라가 요청하면, 마스터가 그 사람의 손패 · 설치 함정 내용을 지금 처리 번호로 그 사람에게만 보낸다. 공개 값은 스냅샷(6절)에서 읽는다 (2026-11-06) |
| 전체 복원 (재접속) | 「내 카드 다시 받기」 의 확장. 끊겼다 돌아온 사람에게 마스터가 **전체 스냅샷**(좌석 · 손패 · 함정 내용 · 전원 HP · 생존 · 찹츄 · 턴 주인 · 진행 방향 · 체인 상태 · 반응 · 턴 마감 시각 · 덱 장수)을 처리 번호와 함께 그 사람에게만 보낸다 (12절, 2026-11-07) |
| 손패 · 함정 다시 보내기 (이주) | 마스터가 바뀌면 각 클라이언트가 자기 손패 · 함정 내용을 새 마스터에게 보낸다 (9.1). 새 마스터만 받는다 |
