**최종 수정일**: 2026-11-14
**분류**: Core

## 1. 목적

카드를 무작위로 지급하고, 소진 시 재생성하는 규칙을 정의한다.

## 4. 동작 — 드로우

```
[클라이언트] 드로우 요청
     ↓
[마스터] 검증: 자신의 턴 + 메인 행동 미사용 + (덱 또는 버림 더미에 카드 존재)
     ↓ 실패 → 거절
[마스터] 덱 맨 위부터 2장(손패가 정확히 9장이면 1장) 제거 → 요청자 손패에 추가
     ↓
[마스터] 요청자에게 카드 내용 전송 (비공개)
[마스터] 전체에 "actorNumber가 1장 드로우함" + 손패 장수 + 덱 잔여 장수 전파 (뽑은 장마다 한 번)
     ↓
[전체]   드로우 연출 (뽑은 본인은 앞면, 나머지는 뒷면)
```

* 턴 드로우(메인 행동)는 **2장** (손패가 정확히 9장이면 **1장** — 딱 10장이 되게) (사용자 2026-11-11, 프로토타입 v2 와 같음 — 「1장」 을 대체). 찹츄 장수가 10 이라 9장에서 2장을 뽑으면 선언할 수 없기 때문이다. 손패가 10장 이상이어도 2장을 뽑는다.
* 뽑는 도중 덱이 비면 버림 더미로 다시 채워 이어 뽑고, 둘 다 비면 **못 뽑은 장마다** 빈 덱 피해를 받는다 (5절) — 그 피해로 HP 가 0 이 되면 남은 장은 뽑지 않는다.
* 드로우는 **항상 덱 맨 위** 카드다.
* 카드 효과에 의한 드로우(A06, A12 등)도 같은 경로를 쓴다. 다만 메인 행동을 소비하지 않는다.

## 5. 예외 — 덱 소진

| 조건 | 처리 | 구분 |
| --- | --- | --- |
| 덱이 0장이 되고 드로우가 필요할 때 | 버림 더미 전체 회수 → 무작위 재셔플 → 새 덱 생성 → 진행 재개 | 확정 |
| 덱과 버림 더미가 **모두** 0장일 때 | 뽑아야 할 1장마다 카드 없이 **피해**를 받는다 (하스스톤 탈진과 같은 방식). 드로우는 그대로 턴 종료. 피해량은 **그 플레이어가 빈 덱에서 뽑은 횟수** — 1 · 2 · 3 … (사람마다 따로 센다, 게임 내내 유지) | 확정 (2026-10-30) / 확정 (피해량, 2026-11-06) |

## 6. 손패

| 항목 | 규칙 | 구분 |
| --- | --- | --- |
| 손패 상한 | **없음.** 11장 이상도 가진다. 찹츄 조건 「정확히 10장」(`07` 4절) 과 충돌하지 않는다 — 10장을 넘기면 찹츄가 아닐 뿐, 뽑기 · 획득은 막히지 않는다 | 확정 (2026-11-07) |
| 손패 내용 공개 | 소유자만 | 확정 |
| 손패 장수 공개 | 전체 | 확정 |
| 손패 정렬 | **뽑은 순서.** 새로 받은 카드는 손패 **오른쪽 끝**에 들어가고, 기존 카드는 자리를 지킨다 (터치 중 카드 자리가 바뀌지 않게). 카드 효과로 받은 카드(상대 손패에서 획득 · 교환 · 전달)도 같다. 카드를 내거나 버리면 그 자리만 빠지고 나머지는 순서를 유지한다 | 확정 (2026-11-07) |
| 최종 사망 시 | 손패 전부 버림 더미로 이동 | 확정 |

`11-card-list.md`의 다수 카드가 다음을 요구한다. **마스터가 손패 내용을 알고 있어야만 구현 가능하다.**

| 요구 | 해당 카드 |
| --- | --- |
| 대상 손패에서 무작위 N장 획득 | A04, A24, T08 |
| 대상 손패에서 무작위 N장 강제 버림 | A05, A15, A23, T07, T11, T12, T14 |
| 손패 전체 교환 | A11, A18 |

## 8. 데이터 구조

| 에셋 | 역할 | 위치 |
| --- | --- | --- |
| `CardData` (ScriptableObject) | 카드 1종의 정의 (id, 이름, 이미지, 타입, 대상, 조건, 효과, 카운터의 반응 대상, 연출 시간 — `10-ui` 5-1) | `Assets/Cards/*.asset` |
| `DeckData.GetCard(id)` | id → `CardData` 조회. 게임에 나오는 카드는 전부 덱에서 나오므로 덱이 사전 역할도 한다 (옛 `CardDatabase` 는 2026-10-10 삭제) |  |
| `DeckData` (ScriptableObject) | 덱 구성 — 카드별 매수 (`Entry { card, count }`). 옛 `DeckRecipe`(ID 반복 목록)를 2026-10-10 이름 · 형식 변경, GUID 유지 | `Assets/Cards/Decks/*.asset` · `Assets/Cards/Main/Deck_Main.asset` |

* 덱 에셋이 카드와 매수를 짝으로 갖는다. 카드 정의(`CardData`)에는 매수를 두지 않는다 — 카드가 무엇인지와 덱에 몇 장인지는 다른 질문이다.
* 덱 구성(어떤 카드를 몇 장)은 **미정**이다.
* 지금 게임 덱은 `Assets/Cards/Main/Deck_Main.asset` — 카드 묶음을 넣는 대로 「카드 가져오기」 가 다시 짠다 (11-card-list 0절). 2026-11-13 묶음 8 까지 넣어 **45장** (묶음 1 의 12장 + 묶음 2 의 17장 + 묶음 3 의 5장 — 107 ×1 · 120 ×3 · 123 ×1 + 묶음 4 의 3장 — 115 ×3 + 묶음 5 의 1장 — 112 ×1 + 묶음 6 의 3장 — 105 ×3 + 묶음 7 의 1장 — 121 ×1 + 묶음 8 의 3장 — 119 ×3). 112 대소동으로 새 판을 열 때도 이 덱 전부로 다시 짠다. 함정 · 카운터는 아직 없다. 시험용 `Assets/Cards/Decks/Deck_Default.asset` 는 rules 시험이 쓴다.
