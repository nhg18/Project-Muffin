# 05. 덱 · 손패 · 버림 더미

**최종 수정일**: 2026-09-25
**분류**: Core

---

## 1. 목적

카드를 무작위로 지급하고, 소진 시 재생성하는 규칙을 정의한다.

---

## 2. 핵심 수치

| 항목 | 값 | 구분 |
| --- | --- | --- |
| 초기 지급 카드 수 | **5장** | 확정 |
| 드로우 위치 | 덱의 맨 위(Top) | 확정 |
| 1회 드로우 장수 | 1장 (메인 행동) | 확정 |
| 덱 총 구성 (카드별 매수) | — | **미정** |

> 초기 손패 수는 `GameStatus.StartHandCount = 5` 한 곳이다 (`DeckPresenter` 가 읽는다). 2026-09-24 통일 완료.
> 단 `GameStatus` 는 MonoBehaviour 의 public 필드라 **씬에 직렬화된 값이 코드값을 덮어쓴다** (규칙 수치를 Inspector 에 두지 않는다 — `CLAUDE.md` 12절). 서버 1층(A1-3)에서 코드 · SO 로 옮긴다.
> 단, 배분 방식은 여전히 각 클라이언트가 `Start()` 에서 5회 요청하는 구조다 (10절).

---

## 3. 동작 — 게임 시작

| # | 처리 | 담당 |
| --- | --- | --- |
| 1 | `DeckRecipe`(카드 ID 목록)로 메인 덱 생성 | 마스터 |
| 2 | 카드 1장마다 **카드 인스턴스 ID** 부여 | 마스터 |
| 3 | 덱 무작위 셔플 | 마스터 |
| 4 | 각 플레이어에게 5장씩 배분 | 마스터 |
| 5 | 각 플레이어에게 **자기 손패 내용만** 전송 | 마스터 → 대상 지정 RPC |
| 6 | 모든 플레이어의 손패 **장수**를 공개 | 마스터 → Player CustomProperties |
| 7 | 덱 잔여 장수를 공개 | 마스터 → Room CustomProperties |

> ⚠ 현재 `Deck.Shuffle()` 은 **빈 함수**다. 덱이 항상 `DeckRecipe` 순서 그대로 나온다.

---

## 4. 동작 — 드로우

```
[클라이언트] 드로우 요청
     ↓
[마스터] 검증: 자신의 턴 + 메인 행동 미사용 + (덱 또는 버림 더미에 카드 존재)
     ↓ 실패 → 거절
[마스터] 덱 맨 위 1장 제거 → 요청자 손패에 추가
     ↓
[마스터] 요청자에게 카드 내용 전송 (비공개)
[마스터] 전체에 "actorNumber가 1장 드로우함" + 손패 장수 + 덱 잔여 장수 전파
     ↓
[전체]   드로우 연출 (뽑은 본인은 앞면, 나머지는 뒷면)
```

* 드로우는 **항상 덱 맨 위** 카드다.
* 카드 효과에 의한 드로우(A06, A12 등)도 같은 경로를 쓴다. 다만 메인 행동을 소비하지 않는다.

---

## 5. 예외 — 덱 소진

| 조건 | 처리 | 구분 |
| --- | --- | --- |
| 덱이 0장이 되고 드로우가 필요할 때 | 버림 더미 전체 회수 → 무작위 재셔플 → 새 덱 생성 → 진행 재개 | 확정 |
| 덱과 버림 더미가 **모두** 0장일 때 | **미정 — 결정 필요** | 미정 |

> ⚠ 현재 코드는 `deck.Count == 0` 이면 `Debug.LogWarning("뽑을 카드가 없음")` 후 아무 일도 하지 않는다. 재생성 미구현.

## 6. 손패

| 항목 | 규칙 | 구분 |
| --- | --- | --- |
| 손패 상한 | 없음 | **가정** (기획에 상한 언급 없음. 찹츄는 "정확히 10장" 조건) |
| 손패 내용 공개 | 소유자만 | 확정 |
| 손패 장수 공개 | 전체 | 확정 |
| 손패 정렬 | **미정** (타입별/ID순/드로우순) | 미정 |
| 최종 사망 시 | 손패 전부 버림 더미로 이동 | 확정 |

### 손패를 조작하는 카드 (요구사항)

`11-card-list.md`의 다수 카드가 다음을 요구한다. **마스터가 손패 내용을 알고 있어야만 구현 가능하다.**

| 요구 | 해당 카드 |
| --- | --- |
| 대상 손패에서 무작위 N장 획득 | A04, A24, T08 |
| 대상 손패에서 무작위 N장 강제 버림 | A05, A15, A23, T07, T11, T12, T14 |
| 손패 전체 교환 | A11, A18 |
| 손패에서 카드 1장 선택해 전달 | A24 |
| 덱 위 N장 확인 후 1장 선택 | A25 |
| 손패 무작위 1장 공개 | C14 |

> ⚠ 현재 구조에서는 **구현 불가능하다.** 손패가 각 클라이언트 로컬에만 존재하고, 마스터는 장수만 안다.
> 이것이 리팩토링에서 가장 먼저 해결해야 할 구조적 문제다. → `docs/refactoring-plan.md`

## 8. 데이터 구조

| 에셋 | 역할 | 위치 |
| --- | --- | --- |
| `CardData` (ScriptableObject) | 카드 1종의 정의 (id, 이름, 이미지, 타입, 대상, 조건, 효과) | `Assets/Cards/*.asset` |
| `CardDatabase` (ScriptableObject) | id → `CardData` 조회 | `Assets/Cards/CardDatabase.asset` |
| `DeckRecipe` (ScriptableObject) | 덱 구성 (카드 ID 목록) | `Assets/Cards/Card pool/*.asset` |

* `DeckRecipe`는 **같은 ID를 여러 번** 넣어 매수를 표현한다.
* 덱 구성(어떤 카드를 몇 장)은 **미정**이다.

## 10. 현재 구현 상태

| 항목 | 상태 |
| --- | --- |
| `DeckRecipe`로 덱 초기화 | 구현됨 |
| 셔플 | **미구현** (`Deck.Shuffle()` 빈 함수) |
| 마스터 경유 드로우 | 부분 구현. 비마스터 요청을 마스터로 위임하지만 **마스터 가드 누락** (`RPC_RequestDrawToMaster`) |
| 초기 배분 | 각 클라이언트가 `Start()`에서 자기 몫 5회 요청. 마스터 일괄 배분 아님 |
| 덱 동기화 | 드로우마다 **덱 전체 ID 배열**을 Room Property로 전송 (규약 위반) |
| 손패 내용 비공개 | 미적용 — `RPC_BroadcastDrawnCard`가 **전체에게** 카드 ID를 보냄 |
| 손패 장수 동기화 | 구현됨 (`PlayerProps.HandCount` = `"handCount"`). 단 마스터가 아니라 **손패 주인이 직접 기록**한다 (09 3절 위반, `PlayerHandPresenter`) |
| 덱 소진 재생성 | **미구현** |
| 버림 더미 | **미구현** |
| 카드 사용 시 손패에서 제거 | 부분 — 요청한 클라이언트가 승인 전에 스스로 지운다 (04 현재 구현 상태와 같음) |
| 상대 손패 장수 보정 | 구현됨 (`OtherPlayerHandPresenter`, 부족분만 보충하고 초과분은 처리 안 함) |
