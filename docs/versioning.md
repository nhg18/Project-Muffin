# 버전 규칙

`MAJOR.MINOR.PATCH` — Player Settings `Version`. 타이틀 좌하단에 `ver {버전} · Project ChapChu` 로 표시된다.

* 숫자 세 자리만 쓴다. `0.3.0-beta` 처럼 글자를 붙이지 않는다 — iOS 는 숫자 세 자리만 받는다.
* 테스트 단계 이름은 버전에 넣지 않고 빌드 이름에만 붙인다. 타이틀 표시에도 넣지 않는다.
* 현재: `0.1.3` · code 4.

## 출시 전 (`0.x.y`)

| 자리 | 올리는 시점 |
| --- | --- |
| MINOR | 점검 빌드마다 (`0.n.0`) |
| PATCH | 같은 점검 안에서 테스트 빌드를 다시 배포할 때 |
| MAJOR | 정식 출시 = `1.0.0` |

테스트 단계가 바뀌어도 번호는 이어서 올린다 (단계마다 되돌리지 않는다).

| 단계 | 하는 사람 | 배포 |
| --- | --- | --- |
| 내부 점검 | 팀원 | PC 빌드 · Play 내부 테스트 · TestFlight 내부 |
| 비공개 테스트 | 초대한 외부 테스터 | Play 비공개 테스트 · TestFlight 외부 |
| 공개 테스트 | 누구나 (할 경우) | Play 공개 테스트 · TestFlight 공개 링크 |

출시 빌드는 마지막 테스트 빌드에서 번호만 `1.0.0` 으로 올려 다시 만든다 (code 도 +1).

## 출시 뒤 (`1.x.y`)

| 자리 | 올리는 시점 |
| --- | --- |
| PATCH | 버그 · 화면 문구만 고친 핫픽스 · **카드 값만 바뀐 패치** (이름 · 문구 · 수치 · 덱 구성) |
| MINOR | 새 기능 · **새 카드**가 하나라도 있는 업데이트 |
| MAJOR | 게임 규칙이 크게 바뀌는 대개편 |

카드는 빌드에 들어 있다 — 카드가 하나라도 바뀐 빌드는 **반드시 버전을 올린다.** 버전이 같으면 카드도 같아야 한다 (`systems/26-card-data.md` 3절 #9, 2026-11-20 PM — 2026-11-19 의 「카드 데이터만 바뀐 패치는 앱 버전을 올리지 않는다」 · 「카드 데이터 번호」 를 뒤집었다).

## 빌드 번호

* Android `Bundle Version Code` 는 기기 · 스토어에 올리는 빌드마다 +1, 재사용 금지. iOS `Build` 도 같은 숫자.
* 버전 변경은 `release/<버전>` · `hotfix/<버전>` 브랜치에서 따로 커밋한다: `chore: 버전 0.2.0 (code 3)`.

## 태그

배포한 빌드마다 `main` 에 `v<버전>` 태그를 단다 — 테스트 빌드(내부 점검 · 비공개 테스트 · 공개 테스트)도 정식 출시와 같다 (PM 2026-11-21).

* 태그는 `release/*` · `hotfix/*` 를 `main` 에 머지한 커밋에 단다. 태그 메시지 = 빌드 이름 (예: `git tag -a v0.2.0 -m "0.2.0 (3) 내부 점검 2차"`). 순서는 skill `git-workflow` 「release · hotfix 순서」.
* 배포 빌드는 그 태그 커밋으로 만든다 — 어느 코드로 만든 빌드인지 태그로 되찾는다.
* 태그는 옮기거나 지우지 않는다. 다시 만들어야 하면 PATCH · code 를 올려 새 태그를 단다 (code 재사용 금지와 같은 이유).
* 어느 브랜치로 내보낼지: develop 에 모인 것을 내보내면 `release/<버전>` (MINOR 든 PATCH 든), 배포한 빌드의 급한 버그만 고쳐 내보내면 `hotfix/<버전>`.

## 빌드 이름

`<버전> (<code>) <단계> <차수>차` — 출시 뒤에는 단계 자리에 `업데이트` · `핫픽스`.

* 예: `0.4.0 (5) 내부 점검 4차` · `0.6.1 (10) 비공개 테스트 1차` · `1.1.0 (24) 업데이트` · `1.0.1 (22) 핫픽스`
* Play Console 「출시 이름」, TestFlight 「테스트할 내용」 첫 줄, QA 기록에 똑같이 쓴다.

## 버전이 다르면 매칭되지 않는다

* 접속할 때 이 값을 Photon `GameVersion` 으로 보낸다 (`PhotonConnection.Connect`). PATCH 만 달라도 나뉜다 (2026-11-12). 테스트 때는 모두 같은 빌드 이름인지 확인한다.
* **카드도 같다** — 카드 값 파일(`cards.json`)이 빌드에 들어 있어, 버전이 같으면 카드가 같다. 그래서 카드가 바뀐 빌드는 버전을 올린다 (위 「출시 뒤」 · `systems/26-card-data.md` 3절 #9).
* 출시 뒤 옛 버전은 Remote Config `minVersion` 으로 막는다 (`systems/23-login.md` 7-6). 새 버전이 Play · App Store **둘 다** 올라간 뒤에 `minVersion` 을 새 버전으로 올린다 — 그 사이에는 옛 · 새 버전끼리 따로 매칭된다.

## 올리는 순서

1. 카드 값은 따로 할 일이 없다 — 머지된 `cards.json` 이 빌드에 같이 들어가고 게임이 읽는다 (`systems/26-card-data.md` 7-3). 새 카드가 있으면 그 카드의 에셋이 커밋돼 있는지만 본다. 값 파일이 틀리면 빌드가 실패한다 (`systems/26-card-data.md` 8절).
2. 위 표로 버전 · code 를 정하고, PM 이 `release/<버전>` 을 develop 에서 딴다 (급한 버그만이면 `hotfix/<버전>` 을 main 에서).
3. 그 브랜치에서 Player Settings `Version` · `Bundle Version Code` · iOS `Build` 를 바꾸고 따로 커밋.
4. 그 브랜치로 빌드해 확인한다 — push 하면 CI 가 확인용 APK 를 만든다 (skill `git-workflow` 「CI · CD」). 나온 버그는 그 브랜치에서 고친다.
5. `main` 에 머지 → 머지 커밋에 `v<버전>` 태그 → `develop` 에도 머지 (위 「태그」).
6. 태그 커밋으로 빌드 → 빌드 이름으로 배포. `v*` 태그를 push 하면 CI 가 서명된 AAB 를 만든다.
7. 카드가 바뀌었으면 노션 「📝 패치 노트」 의 「버전」 칸에 이 앱 버전을 적는다.
8. (출시 뒤) 두 스토어에 다 올라가면 `minVersion` 을 올린다 — 옛 앱은 켰을 때(앱을 켜 둔 사람은 로비에서 방에 가려 할 때) 「업데이트 필요」 에서 멈추고 스토어로 간다 (`systems/23-login.md` 7-6). 카드 패치는 이때 모두에게 닿는다.
