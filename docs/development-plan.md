## 0. 결론 먼저

**100% 의 정의**: `systems/` 의 확정 규칙이 전부 구현되고, 미정 항목이 전부 확정되어 구현되고, 모바일 기기에서 4인 1판이 로그인부터 결과 화면까지 완주되며, 스토어에 올릴 수 있는 빌드가 나온 상태. 버전 `1.0.0`.

**지금 위치** (2026-09-25 코드 대조 결과):

| 영역 | 완성도 | 근거 |
| --- | --- | --- |
| 아웃게임 (접속 · 타이틀 · 로비 · 방 · 팝업 · 화면 규격) | 약 90% | 디자인 교체 · 실기 QA 만 남음 |
| 인게임 (시작 시퀀스 · 턴 · 덱 · 카드 · 체력 · 승리 · 인게임 UI) | 약 25% | 마스터 소유 원본 없음, 게임이 끝나지 않음, 인게임 씬 없음 |
| 카드 59장 | 5% | 테스트 4장, 효과 타입 1 / 24 |
| 로그인 · 재접속 · 결과 화면 | 0% | 문서도 없음 |

**남은 길은 8단계다.** M0 은 끝났다. M1~M5 가 MVP(`0.5.0`), M6~M8 이 완성(`1.0.0`).

```
M1 마스터 권한 · UI 재연결 → M2 카드 파이프라인 · 함정 → M3 체력 · 턴 · 승리 (게임이 끝난다)
→ M4 카드 59장 → M5 MVP 마감 (0.5.0) → M6 안정화 · 밸런스 → M7 로그인 · 친구 → M8 완성도 (1.0.0)
```

병렬화 장치는 v1 과 같다. **계약(`GameEvents` · `IGameRequests` · `IGameState` · `PlayerProps`/`RoomProps`)을 먼저 올리고, B 는 `FakeGameServer` 로 개발한다.**
v1 과 달라진 점은 4-1절.

## 5. 운영 규칙 (v1 유지 + 2건)

1. **씬 · 프리팹은 B 단독.** A 는 `.cs` 만 만진다.
2. **브랜치는 작업 단위.** 한 PR 에 폴더 이동과 로직 변경을 섞지 않는다.
3. **계약 4종 변경 PR 은 양쪽 리뷰 필수**, 나머지는 셀프 머지.
4. **`GameServer` 는 Photon 없이 EditMode 테스트 가능하게 설계한다** (A1-2 asmdef 이 전제).
5. **`FakeGameServer` 는 끝까지 버리지 않는다.** 규칙은 흉내만 낸다.
6. 🆕 **연습 코드는 실제 계약 위에서만 쓴다.** 계약을 복사한 별도 네임스페이스(옛 `Chapchu.Practice`)를 만들지 않는다.
7. 🆕 **문서의 "현재 구현 상태" 절은 코드를 바꾼 PR 이 같이 고친다.** 낡은 경고가 남으면 다음 세션이 잘못된 전제로 시작한다 (2026-09-25 에 7곳 정리).
8. 하지 말아야 할 것은 [`refactoring-plan.md`](refactoring-plan.md) 5부.
