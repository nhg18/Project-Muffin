## 0. 결론 먼저

**일정은 v2 와 같다.** M1 은 9/28 시작, MVP `0.5.0` 은 12/2, 출시 `1.0.0` 은 2027-01-25.

**v4 의 변경: 1단계를 "샌드박스"로 만든다.** 규칙 검사와 카드 효과 없이, 실제 게임 화면으로 종이 카드처럼 뽑고 · 내고 · 치우고 · 체력을 바꾸는 온라인 카드 테이블이다 ([`systems/18-sandbox.md`](systems/18-sandbox.md)).

* 샌드박스는 **실제 서버의 첫 층**이다. 방장 기기가 상태 원본을 쥐고 비공개 정보를 지키는 부분은 규칙 모드와 똑같다. 규칙은 2단계부터 **그 위에 검사층 · 효과층을 켜서** 붙인다. 따로 만든 임시 도구를 나중에 버리는 방식이 아니다
* 목표일: **10/9(금) 첫 샌드박스 플레이테스트**, 10/11 1단계 게이트
* 얻는 것: 기획이 카드 59장을 실제 화면으로 시험한다(카드 숫자 확정 11/4 전에). UI 화면이 로직 규칙을 기다리지 않는다. 수동 조작은 규칙이 붙은 뒤 테스트 도구로 남는다
* 비용(추정): 로직 2~3일 · UI 3~4일 추가. 대신 옛 1단계의 좌석 · 손패 정리 작업이 샌드박스 화면 작업에 합쳐진다

> 기획 · 디자인 트랙(C · D)은 사용자 검토 전 **보류**다 (2026-09-26). 아래 단계 표의 기획 · 디자인 행은 v3 제안 그대로 두었다.

**팀의 병목은 개발 2명이다.** 나머지 4명의 일은 한 문장으로 요약된다.

> **개발자가 멈추지 않도록, 개발자가 필요로 하기 전에 결정과 시안을 준비해 둔다.**

그래서 v3 의 핵심 규칙은 하나다.

> **한 마일스톤 앞서 간다.** 개발이 M(n) 을 만드는 동안 기획과 디자인은 M(n+1) 을 준비한다.

```
기획 (규칙 · 흐름 결정)  →  디자인 (시안)  →  개발 (구현)  →  기획 (게이트 검증 · 플레이테스트)
        한 단계 앞               한 단계 앞            지금 단계             지금 단계
```

| 역할 | 한 줄 임무 |
| --- | --- |
| 로직 개발 | 마스터 서버 · 규칙 · 카드 효과 (v2 A 트랙 그대로) |
| UI 개발 | 화면 구현 · 입력 · 연출 · 씬, 디자인 에셋을 Unity 에 반영 (v2 B 트랙 + 에셋 반영) |
| 기획 R (규칙 · 카드) | 미정 규칙 결정, **카드 59장 수치 · 이름 · 문구**, 밸런스, 종이 프로토타입 |
| 기획 X (화면 · 경험) | 화면 흐름 · 문구 결정, 새 문서(결과 · 로그인 · 튜토리얼), **플레이테스트 · QA 운영** |
| 카드 디자인 | 카드 프레임 · 뒷면 · 아이콘 · 일러스트 59장 · 이펙트 · 키 아트 |
| UI 디자인 | UI 디자인 시스템 · 모든 화면 시안 · 슬라이스 에셋 · 앱 아이콘 · 스토어 이미지 |

**기획 2명은 게임 개발이 처음이다.** 그래서 기획 트랙은 세 가지 도구로만 일한다 (상세는 `plan-c-planning.md`).

1. **종이 프로토타입** — 카드 게임이라 코드 없이 종이로 규칙과 수치를 먼저 시험할 수 있다
2. **결정 요청서 양식 하나** — 모든 미정 항목을 같은 양식으로 풀고, 수요일 회의에서 확정한다
3. **게이트 체크리스트** — 각 마일스톤 끝의 "되는지 확인"을 기획이 맡는다. 규칙을 가장 잘 아는 사람이 검증한다

두 기획자 중 누가 R · X 를 맡을지는 본인 선호로 정한다.

**계약 4종은 개발 2명의 공동 소유다** (v2 와 같음): `PlayerProps`/`RoomProps` · `GameEvents` · `IGameRequests` · `IGameState`. 변경 PR 은 양쪽 리뷰.

## 2. 일하는 방식

### 2-1. 주간 리듬

| 요일 | 무엇 | 참석 | 진행 | 길이 |
| --- | --- | --- | --- | --- |
| 월 | 주간 계획 — 이번 주 할 일 · 막힌 것 | 전원 | 기획 X | 20분 |
| 수 | **결정 회의** — 이번 주 결정 요청서를 확정 / 보류 | 기획 2 + 해당 개발자 · 디자이너 | 기획 R | 30분 |
| 금 | **플레이테스트** — M1 ~ M2 는 종이, M2 게이트 이후는 빌드 | 전원 | 기획 2 | 40분 |
| 매일 | 한 줄 공유 (디스코드) — 어제 한 것 · 오늘 할 것 · 막힌 것 | 전원 | — | — |

### 2-2. 결정 절차 (미정 → 확정)

1. 담당 기획자가 **결정 요청서**를 쓴다 (양식은 `plan-c-planning.md` 3절). 선택지 2~3개와 추천안이 반드시 있다.
2. 선택지마다 해당 개발자가 **구현 난이도 한 줄**을 단다 (상 · 중 · 하 + 이유). 회의 전날까지.
3. 수요일 결정 회의에서 확정하거나 보류한다. **최종 결정권자는 팀장이다 — 아직 정하지 않았다면 M1 첫 월요일에 정한다.**
4. 확정되면 담당 기획자가 `docs/systems/` 해당 문서를 고치고 `확정` 을 붙인다 (GitHub 웹 편집 → PR → 해당 개발자 1명 리뷰). 처음 2주는 UI 개발이 옆에서 같이 한다.
5. **문서에 `확정` 이 붙어야 개발이 구현한다** (`CLAUDE.md` 0절). 노션 결정은 구현 근거가 아니다.

> **틀려도 된다.** 수치 · 매수 · 문구는 ScriptableObject 값이라 나중에 바꾸는 비용이 작다. 늦게 결정하는 비용이 틀리게 결정하는 비용보다 크다.

### 2-3. 전달 규칙

| 보내는 쪽 → 받는 쪽 | 무엇을 | 어디로 |
| --- | --- | --- |
| 기획 → 개발 | 확정된 규칙 · 수치 · 문구 | `docs/systems/*.md` (노션 아님) |
| 기획 → 디자인 | 화면 흐름(어떤 순서로 무엇이 보이는가) · 카드 이름 · 카드 문구 | 노션 페이지 + `systems/` 링크 |
| 디자인 → UI 개발 | 시안 링크 + 슬라이스 PNG + 규격표(크기 · 9-slice 여백 · 색 hex · 폰트) | 공유 폴더 `/handoff/날짜_화면이름/` |
| 개발 → 기획 | 게이트 빌드 + 확인할 항목 | 디스코드 + 게이트 체크리스트 |

## 3. 단계별 플랜 (6인)

각 단계는 **게이트**로 끝난다. 게이트 확인은 기획 X 가 체크리스트로 진행하고, 개발자가 빌드를 띄운다.
개발 작업 번호(A1-1, B1-0 …)는 트랙 문서 `plan-a-logic.md` · `plan-b-ui.md` 를 따른다. 기획 · 디자인 작업은 `plan-c-planning.md` · `plan-d-art.md`.

### M1 — 샌드박스 (9/28 ~ 10/11)

**목표**: 규칙 없는 온라인 카드 테이블. 4명이 실제 게임 화면에서 뽑고 · 내고 · 치우고 · 함정 놓고 · 체력을 바꾸고 · 턴을 넘긴다. 방장 기기가 상태 원본을 쥐고, 손패 내용은 본인에게만 간다.

| 역할 | 할 일 | 마감 · 산출물 |
| --- | --- | --- |
| 로직 | A1-1 **약속 먼저** — 카드 이동 알림(공개 · 비공개), 샌드박스 요청 약속 신설, `IGameState` 리뷰 → A1-2 테스트 환경 → A1-3 서버 1층(영역 · 카드 번호 · 체력 · 턴 · 찹츄 표시, 순수 C#) → A1-4 섞기 · 재생성 · 시작 순서 → A1-5 Photon 연결(비공개 전달) → A1-6 샌드박스 스위치 → A1-7 옛 동기화 코드 정리 | **10/1 약속** · 10/6 서버 1층 · 10/9 Photon |
| UI 개발 | B1-0 GameScene 재구성 · 영역 배치(덱 · 가운데 · 버림 · 함정 칸 · 좌석 · 손패) → B1-1 로컬 서버(처음엔 흉내, 서버 1층이 나오면 그걸 로컬로 돌림) → B1-2 영역 화면 → B1-3 모바일 조작 입력 · 행동 로그 → B1-4 카드 표 가져오기 도구(59장, 효과 없이) → B1-5 방 화면 샌드박스 토글 → B1-6 Photon 서버로 교체 · 옛 로직 제거 | 10/7 로컬 동작 · **10/9 4클론** |
| 기획 R | 온보딩 · 덱 구성 v0 (10/4) · 1주차 종이 테스트 → **10/9 첫 샌드박스 플레이테스트** | 10/4 · 10/9 |
| 기획 X | 온보딩 · 카운터 · 체인 · 함정 흐름 v0 (10/11) · 샌드박스 플레이테스트 기록 | 10/11 |
| 카드 디자인 | 카드 규격 (10/2) · 프레임 3종 · 뒷면 · 아이콘 (10/11) | v3 제안 그대로 (보류) |
| UI 디자인 | 디자인 규칙집 (10/4) · 인게임 배치 스케치 (10/7) — 샌드박스 영역(가운데 · 버림 · 함정 칸 · 행동 로그) 포함 | v3 제안 그대로 (보류) |

**게이트**: 샌드박스 방에서 4클론이 —
① 섞인 덱에서 5장씩 받고 상대 손패는 뒷면 · 장수만 보인다
② 카드 내기 · 대상 화살표 · 가운데 치우기 · 버리기 · 주기 · 무작위 가져오기 · 함정 놓기 / 공개 · 체력 바꾸기 · 턴 넘기기 · 찹츄 표시 · 5초 타이머가 네 화면에서 같다
③ 주기 · 가져오기로 옮긴 카드 내용은 받은 사람만 본다
④ 덱에 카드 59장(문구만)이 들어 있다
⑤ 서버 1층이 에디터 테스트(섞기 · 이동 · 비공개 · 시작 순서)를 통과한다

**목표**: 샌드박스 서버 위에 검사층과 효과층을 켠다. 규칙 모드에서 카드 한 장이 사용 → 반응 5초 → 체인 역순 → 버림 더미까지 자동으로 처리된다. **샌드박스는 계속 켤 수 있다.**

## 7. 운영 규칙

1. 씬 · 프리팹 · Unity 에셋 반영은 **UI 개발만** 한다. 디자이너는 저장소를 만지지 않는다.
2. 로직 개발은 `.cs` 만 만진다.
3. 브랜치는 작업 단위. 한 PR 에 폴더 이동과 로직 변경을 섞지 않는다.
4. 계약 4종 변경 PR 은 개발 2명 모두 리뷰한다.
5. 서버 코드는 Photon 없이 에디터 테스트가 가능하게 만든다.
6. 로컬 서버(옛 `FakeGameServer`)는 끝까지 유지한다. 서버 1층이 나온 뒤에는 흉내 코드를 지우고 진짜 서버 코어를 돌린다.
7. 연습 코드도 실제 계약 위에서만 쓴다.
8. 코드를 바꾼 PR 이 문서의 "현재 구현 상태" 절도 같이 고친다.
9. **구현 근거는 `docs/systems/` 의 `확정` 뿐이다.** 노션 · 디스코드 합의는 문서에 옮겨질 때까지 구현하지 않는다.
10. **한 마일스톤 앞서 간다.** 기획 · 디자인이 개발보다 늦으면 월요일 회의에서 바로 드러내고 범위를 줄인다.
11. 🆕 **샌드박스는 규칙을 흉내 내지 않는다.** 검사 · 효과는 서버 2 · 3층에서 한 번만 만든다. 화면에서 "내 턴이 아니면 막기" 같은 판정을 넣지 않는다.
12. 🆕 **샌드박스는 출시판에 넣지 않는다.** 개발 빌드에서만 켤 수 있다.
13. 하지 말아야 할 것은 [`refactoring-plan.md`](refactoring-plan.md) 5부.
